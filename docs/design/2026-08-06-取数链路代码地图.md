# 取数链路代码地图 —— 从 skill 到数据库

`common/access.py` 往下都有什么、各自负责什么、改东西该去哪。

> 本篇讲 **skill 侧**的链路。中间件自身的协议、报文结构、与客户环境的逐层
> 对照见 [`2026-07-31-grmp-middleware-架构图.md`](2026-07-31-grmp-middleware-架构图.md)。

## 总览：一个分叉，两条路，共用一份脚本定义

```
                      skill 代码（13 个）
                sqltune.py / health.py / …
                            │
                            │  runner = access.for_conn("og-grmp")
                            │  runner.run("sqltune.tables", {...})
                            ▼
        ┌───────────────────────────────────────────┐
        │  common/access.py:193  runner_for_conn()   │
        │  ★ 唯一的选路点，按 conn.driver 分叉        │
        └───────────────────────────────────────────┘
                 │                          │
   driver=pg8000/gsql                  driver=grmp
                 │                          │
                 ▼                          ▼
   ┌──────────────────────┐   ┌──────────────────────────┐
   │ grmp/runner.py       │   │ grmp/client.py           │
   │ DirectRunner         │   │ GrmpClient + GrmpRunner  │
   │ 本进程内连库          │   │ HTTP → 8769              │
   └──────────────────────┘   └──────────────────────────┘
                 │                          │
                 │                     ╭────┴──── 进程边界 ────╮
                 │                     │  grmp_middleware/     │
                 │                     │  grmp_mock/           │
                 │                     ╰────┬──────────────────╯
                 │                          │
                 └──────────┬───────────────┘
                            ▼
                    openGauss  og:5433
```

**两条路返回的东西形状完全一样**（全字符串化的行字典）。这就是这一层的全部
价值：skill 代码在本地与客户环境完全相同，不需要为两边各留一套。

## 直连路径：`DirectRunner`

```
runner.run("sqltune.tables", {"names": "'orders'"})
   │
   ├─▶ grmp/registry.py     rglob("*.yaml") 扫 scripts/registry/
   │   grmp/script.py       解析 + 校验 yaml → ScriptRecord
   │        └─ 得到 script_content 与 params 声明
   │
   ├─▶ grmp/placeholder.py  render()：{{names}} 文本替换 + 类型校验
   │
   ├─▶ common/db.py         Database.connect() → backends/pg8000_backend.py
   │        └─ 只读会话，SET statement_timeout
   │
   ├─▶ grmp/columns.py      check_columns()：列名重名就报错
   │        两个 ?column? 会互相覆盖，静默少返回一列
   │
   └─▶ grmp/serialize.py    result_array()：**全部字符串化**
            刻意复刻客户中间件的信息损失，不「改良」——
            改良了，本地写的解析代码到客户环境会全部失效
```

## 中间件路径：`GrmpClient` → HTTP

```
runner.run("sqltune.tables", {"names": "'orders'"})
   │
   ├─▶ client.py:107  _id_map()      ┐
   │      POST /common-operations     │ 接口一：取命令清单
   │      逻辑名 → id 的映射，进程内缓存 │ 每进程只调一次
   │      ★ id 是环境相关数据，绝不硬编码 ┘
   │
   └─▶ client.py:131  invoke()
          POST /common-operations/invoke
          {dataIp, id:"70", param:[{param_name, param_value}]}
          头名是 auth（不是 Authorization，无 Bearer 前缀）
```

**为什么必须先查清单。** 客户文档里 `id=56` 是「查看数据库信息」，而调用示例里
同一个 `id=56` 传的是慢 SQL 的参数。硬编码的失败方式是：换环境后 id 依然存在、
指向另一条脚本、执行成功、结果无关、**不报错**。

## 共用层：两条路走同一份脚本定义

```
                scripts/registry/*/*.yaml
                    90 条脚本定义
                          │
          ┌───────────────┴───────────────┐
          ▼                               ▼
    DirectRunner                    grmp_register.py
    运行时直接读                      灌进 store.py 的 SQLite
                                          │
                                    executor.py 从库里取
```

同一份 yaml 喂两条路，所以「本地跑通、换条路径就错」无处可藏。
`tests/test_dual_path_live.py` 钉的就是这个。

## 三个能力位，不是三处 `if driver == "grmp"`

`access.py:37-56`：

```python
DIRECT_DRIVERS        = {"gsql", "pg8000"}
_WHITELIST_ONLY       = {"grmp"}    # 只跑已注册脚本
_STATELESS            = {"grmp"}    # 无跨语句会话
_NO_STATEMENT_TIMEOUT = {"grmp"}
```

**skill 代码里不该出现任何 driver 名字。** explain 曾经写死 `driver == "grmp"`：
将来客户换一种白名单型中间件，那句判断会静默放行，错报到中间件那边去，
排查方向整个被带偏。所以 skill 表达「我需要什么能力」，由这里回答给不给得了。

**白名单**和**无状态**是两根独立的轴。今天恰好都只有 grmp 缺，但别合并 ——
`gsql` 就是「能跑任意 SQL、但没有持久会话」的现成反例。

### 拒绝路径（`og-grmp` 上 hypopg 与任意 SQL 走不通的实际执行点）

| 入口 | 位置 | 对 `driver: grmp` |
|---|---|---|
| `runner_for()` | `access.py:193` | 走 `GrmpRunner`，只能执行已注册脚本名 + 参数 |
| `session_for()` | `access.py:124` | 抛 `SessionUnavailable` —— **不降级、不回退** |
| `connection_for()` | `access.py:158` | 抛 `UnregisteredSqlUnsupported` |

不静默回退是关键：回退了，报告会声称走了中间件而数据其实来自直连，
中间件模式的真实表现就测不出来。

## 报错怎么归一

```
   pg8000 抛异常 ──┐
                   ├──▶ grmp/errors.py  QueryError  ──▶ skill 的降级逻辑
   HTTP 非 200  ──┘         （唯一的对外失败类型）
```

skill 只 catch 一个 `QueryError`。新增一种访问方式时，新 Runner 抛它即可，
**13 个 skill 一行不用改**。

## 一句话定位

| 想改什么 | 去哪 |
|---|---|
| 加一种访问方式 | `access.py:193` 加分支 + `access.py:37-56` 的能力位 |
| 改协议报文 | `common/grmp/client.py` |
| 改中间件行为 | `grmp_middleware/grmp_mock/server.py` |
| 加/改脚本 | `scripts/registry/<skill>/*.yaml`，然后重新注册 |
| 改取值还原 | `common/grmp/values.py`（`bool("f")` 是 `True` 那个坑在这里） |

## 怎么现场核实「是不是真走了中间件」

```bash
tail -f /tmp/grmp_mock.log
```

skill 每取一次数就滚一行。实测一次 sqltune 产生 17 行：接口一 1 次（取清单）
＋ 接口二若干次（逐条执行）。若某个 skill 的输出出来了而日志一动不动，
就说明它绕过去了 —— 目前没有这样的路径，但这是最直接的验证手段。
