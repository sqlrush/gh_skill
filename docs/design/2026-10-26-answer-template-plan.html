0 · 一页结论

做法:一份模板正文,注入到每个技能;能用脚本算的都放进脚本;回答格式用检查工具验收。 模板规则写一份(common/answer_templates/),照「安全红线」现成的做法注入到各技能的 SKILL.md 和 AGENTS.md, 守卫测试保证各份副本逐字一致 —— 不会出现这个技能改了、那个技能没改。SQL 的耗时趋势、突然变慢的时间点、执行计划有没有变, 由脚本算好交给模型转述,不让模型自己拿数字去推。

用户看到的变化:

  • 每类问题的回答顺序固定:先总体状态和一段短结论,再按固定的几段展开,最后给 1–3 条「需要就 xxx 展开说明吗?」。
  • 每一段先用应用的话说清影响,再接着讲数据库机制,开发人员和数据库工程师各取所需。
  • 排查类回答里,出自知识库的句子上色,句后括号写「(引用自 xxx 库 编号)」,不再单列一节「客户知识库参照」; 知识问答在第一行写「解答来源」。客户知识蓝色,官方文档青色。
  • SQL 优化多了「现状与趋势」:平均 / 最大耗时、近 7 天按小时的变化、哪个时间点突然变慢、那时执行计划变没变。
  • WDR 解读有专门的版式(R7,第 2.3 节):先回答「这段时间库忙不忙、时间花在哪」,再逐条讲问题和引发它的语句;全景数据表挪到附录。版式由脚本渲染,不靠提示词。
要你定的 4 件事(详见第 9 节):① 客户 AGENTS.md 里原有的输出格式、引用格式与兜底说法和新模板冲突,怎么处理; ② 需求里没有覆盖的几类回答(WDR、Top SQL 榜单、参数体检、存储过程调优)按我的建议套用;③ 3 条新增白名单脚本客户登记之前,SQL 优化第 ① 段怎么降级;④ WDR「两段对比」解读要不要这次一起做。

2 · 模板总览

2.1 共用的开头与结尾

① 评估时段只在问某段时间时:要的是哪段、实际评估的是哪段、为什么(现行规矩) ② 总体状态带级别(以脚本为准)+ 驱动一句 + 判断校验(不变) ③ 短结论2–4 句,开发人员也看得懂 ④ 正文按问题类型分段,见下 ⑤ 展开提议1–3 条「需要就 xxx 展开说明吗?」

知识问答没有严重级别,不放 ② 总体状态带;正文第一句就是直接答案,起短结论的作用。SQL 优化的总体状态带写「验证状态」(已验证收益 / 未找到已验证方案)。

2.3 WDR 解读(R7,建议)

WDR 和健康检查都是「某段时间的整体分析」,但用户看 WDR 最想知道的是这段时间库忙不忙、时间花在哪、是哪几条语句造成的。 所以在 R1 四段的基础上按 WDR 的特点改了每段的内容:

位置内容与现在的区别
开头评估窗口(快照 A → B、时长,和所问时段差多少)→ 总体状态带 → 短结论(≤3 句)短结论从「模型在渲染结果前面自己加的 3 行」改成 interp.json 里的字段,由脚本排版
① 负载画像这段时间库在忙什么:数据库时间多少、构成(CPU / IO / 锁 / 其它等待);事务数、逻辑读 / 物理读、落盘量;有贵行基线的并列给出现在散在「维度概览」和「全景分析」里,改成一段先回答「忙不忙、忙在哪」
② 问题与元凶逐条高风险发现:现象 → 证据 → 根因 → 引发它的语句;Top SQL 多维表与「各维度元凶」行放在这里,作为找元凶的证据现在「高风险发现」在全景表后面;Top SQL 多维表照旧原样保留(这是之前定的硬要求)
③ 解决方案按 P0 / P1 / P2:每条元凶语句怎么优化(只放 sqltune 验证过的,带真实倍数);锁类给事务与并发层面的改法;风险、需人工执行现在建议挂在每条发现下面,没有排优先级
④ 总结和结论总结 + 建议 + 需要用户配合的事;原生 WDR 报告与大盘链接;展开提议(例如「需要就 sql_id … 做调优吗?」)新增
附录其余全景数据(Checkpoint、Cache、File IO 等,每张一句判读)、图示、SQL 附录(原文与真实执行计划)、本报告没覆盖的、校验区(模型遗漏 / 未锚定 / 未验证建议)从正文中间挪到最后
  • 两种读者:interp.json 的每条发现多两个字段 —— 应用视角(业务感受到什么、哪类写法引起的)、数据库机制;脚本排成两段。
  • 知识引用:interp.json 里写引用的编号和那句话,由脚本统一上色、加「(引用自 … 编号)」,渲染时就核对编号在不在库里 —— 比靠模型手写标签更稳。
  • WDR 特有的几条规矩照旧:窗口几乎空闲时不判比例;Top SQL 与原生 WDR 报告交叉核对,榜单不全以原生报告为准并说明; 各维度的元凶分开归因(10-21 那一轮,落盘占 86% 的语句不在按耗时排的前 10 名里);数据库时间自洽检查。

2.4 两种读者怎么写(R2)

应用视角18:32 起,更新账户余额的那条语句平均要等约 90 秒才返回 —— 对业务来说就是转账类交易超时。 不是语句本身慢,而是它在排队等别的交易放锁:前面有交易改了同一批账户还没提交。

数据库机制还是这批会话:它们都在等同一行上的 transactionid 锁(ShareLock), 阻塞链 5 层,根会话持有行锁未提交;等锁期间 CPU 几乎为 0,所以按 CPU 找元凶会扑空,要按锁等待找根会话。

  • 第二段接着第一段的同一件事(同一条语句、同一批会话)往下讲,不另起话题 —— 这是「不割裂」。
  • 应用视角用业务能感知的词:交易超时、接口变慢、批量跑不完;尽量说「应用里哪类写法会导致它」。
  • 机制段可以用术语,但每个结论仍要落到这次采到的数字上;讲机制不等于可以没有证据就提内核参数调整。
  • 示意,数字取自 10-21 演练第一轮(锁等待约占 90%,UPDATE 平均约 90 秒)。

排查类(R5):不说「根据知识库」,句子上色,句后括号写出处

DDL 变更时,会话级的锁等待上限不超过 30 秒(引用自贵行规范库 GS-CHG-003)。 本行出现过同一现象:多个会话插同一主键排队,根会话是 active 而不是空闲事务(引用自本行案例库 S3-20260416-FPAYS-…)。 lockwait_timeout 的默认值是 20 分钟(引用自 GaussDB 官方文档库 PD-G25132C-编号)。

知识问答(R6):第一行先写解答来源

解答来源:GaussDB 官方文档库 PD-G25132C-编号;贵行规范库 GS-CHG-003(两者不一致,以贵行规范为准)

lockwait_timeout 默认 1200000 毫秒(20 分钟)[1];贵行要求 DDL 变更时会话级设置不超过 30 秒[2]。

用到多条时句后只写编号 [1][2],对应第一行的来源;只用到一条时不逐句标。

  • 颜色:客户知识沿用现在的蓝色 #2f6fdb;官方文档换青色 #0f7c86(都用对话界面已支持的 <font color=…> 标签)。括号不上色。

② SQL 文本和执行计划解读

SQL 原文 → 计划树(瓶颈节点标 [P1]…)→ 计划走查 → 根因 → 证据链摘要(「慢在哪里」)。

③ 怎么优化

每个已验证方案:改动 · 为什么 · 证据 · 风险,外加前后对比:
若方案是改写,另有文本差异(示意另一条 SQL):
- WHERE to_char(o.created_at,'YYYYMMDD') = '20261021'
+ WHERE o.created_at >= '2026-10-21' AND o.created_at < '2026-10-22'
计划:Seq Scan on orders  →  Index Scan using …           ← 前后两棵计划树并排
cost:X → Y(N×)                                    ← 照抄验证结果,不自己算
耗时:优化前平均 … ms(实测) → 优化后 需实测          ← 不拿 cost 倍数换算耗时

没通过验证的单独列「未验证想法」,不和已验证的放在一起。

4 · 怎么实现

4.1 一份模板正文,注入到每个技能

为什么要注入到每个 SKILL.md、而不是只写在 AGENTS.md:客户换技能目录时不一定换 AGENTS.md(2026-09-10 安全红线那次就是这样丢的); 而模型执行某个技能时最先照着读的是那个技能的 SKILL.md。AGENTS.md 里放跨技能的部分:归类规则、知识问答、跨技能的故障排查。

4.5 SQL 优化:现状与趋势(R4 第 ① 段)

新增白名单脚本(sqltune 域,只读)取什么脚本怎么用

4.6 WDR:版式由脚本渲染(R7)

  • SKILL.md 第 7 步:说明新字段怎么写;「最终报告 = render 原样输出」这条不变,但不再需要模型在前面自己加摘要。

附 A · 关联现象清单(初稿,请你审)
