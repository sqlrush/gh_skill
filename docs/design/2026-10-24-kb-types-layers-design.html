要点做法
类型是「标签 + 按类型的必填要点」类型决定这条知识必须记什么（规范要审批与生效版本，缺陷要受影响版本与厂商结论，手册要前提与回退……），导入时校验；不是只贴个名字。
谁打标签导入时模型提议、人确认、脚本校验——和现在「条款化 / 案例化」的分工一样。确认清单里多一列「类型」。
分层靠「生成 + 命令」，不是只拆文件L2 条目是唯一需要人维护的正文；L0、L1 由 kb.py index 从 L2 的元数据和图谱生成，有大小上限；模型通过 topic / show / evidence 逐层取，不再整份读 RULES.md / CASES.md。
L0「每次诊断先读」由脚本保证9 个诊断技能的脚本已经在输出里自动附「客户知识库参照」；这一节的开头改成 L0 摘要（含本实例的环境画像），模型不用自己记得去读。
新增四类此前没有的知识环境与业务画像、指标口径与正常基线、已知缺陷与版本例外、处置与恢复手册——它们让「这条知识适不适用于本环境」可以判断（版本、部署形态、批量窗口）。
反例「看起来相同、根因不同」的案例在 L1 里并排展示，并要求写区分证据；导入时发现同症状不同根因而没写区分证据，审核清单会提示。
兼容旧知识库不迁移也能用（类型显示「未分类」）；kb.py migrate 给存量条目提议类型与专题，人确认后落盘。RULES.md / CASES.md 再保留一个版本。

1　需求与现状

1.1 需求（2026-10-24）

  1. 知识类型标签：参考下表的 8 类，对导入的知识打类型标签；每类有自己的记录重点。另补两样：现场背景与判断边界；尤其要保存「看起来相同，但根因不同」的反例，案例必须记下区分它们的证据。
  2. 渐进式披露：知识库的 md 按 L0 / L1 / L2 / L3 拆分和组织；要有明确的读取机制，仅仅拆成很多 md 还不够。
层次内容何时读取
L0总索引知识范围、专题入口、适用环境每次诊断先读
L1专题导航症状、同义词、候选原因、相关条目摘要按问题选择
L2知识条目完整规范、案例或排查步骤命中后读取
L3原始证据原文、照片、日志、报告核对细节或处理冲突

建议的导入顺序：最小环境画像和现行规范 → 高频故障案例及排查步骤 → 对应产品章节 → Wiki 持续补齐。不必先把全部产品手册搬完。

1.2 现状

现在有的形态缺口
rules/*.yaml 条款GS-域-NNN，severity / check / applies / keywords没有「审批与变更要求」「生效版本」
cases/*.md 案例S1–S4 ID；现场 / 判断 / 处置 / 复发标志；结论强度「判断」一段写完，看不出候选原因、取证顺序、排除理由、最终验证；没有反例 / 区分证据
guides/*.md 指南id + description，自由正文产品文档、Wiki 经验、操作手册混在一起；不分产品系列与版本——openGauss / PostgreSQL 的行为可能被当成 GaussDB 的
errata/ 修正首行一句结论契约说它优先级最高，检索时却没有加权
sources/、原始工单、kb-init 的照片原文快照，只读条目和原文之间没有可回指的「证据」链接
INDEX.md / RULES.md / CASES.mdindex 生成的平铺清单；契约要求判定前整份读 RULES.md条目一多就读不动、也读不完；没有按问题选择的入口
——完全没有：环境与业务画像、指标口径与基线、已知缺陷、处置手册。于是「这条知识适不适用于本环境」无从判断
现有的检索（词法 + 向量 + 图，按每条发现自动附「客户知识库参照」）保留不动，是这次改造的底座；改的是条目的结构、层与层之间怎么走，以及输出给模型的量。

2.3 怎么判定类型（导入时给模型的规则，人最终确认）

这段内容在说什么类型
「必须 / 禁止 / 需审批 / 自某日起执行」公司内部规范
某一次故障从发现到恢复的经过历史案例排查思路
某个系统是什么样：版本、拓扑、连接池、批量环境与业务画像
某个指标怎么算、平时多少指标口径与正常基线
某版本有缺陷、打什么补丁、厂商怎么说已知缺陷与版本例外
遇到某情况按什么步骤做、怎么回退处置与恢复手册
出自 GaussDB 官方文档 / 产品手册高斯产品文档
其余的经验总结、技术帖存量 Wiki 经验
一个条目一个主类型。一篇 Wiki 里同时有规定、步骤和经验时，拆成多个条目（规范 + 手册 + 经验），共用同一份 L3 原文；不做多类型标签——多类型会让必填要点没法校验，L1 里也会重复出现。

2.4 反例：看起来相同、根因不同

例如「连接数打满」，可能来自业务增量、锁阻塞，也可能是应用连接泄漏。做法：

  • kb.py index 从图谱里找出同一症状节点、不同根因的案例组，在该专题的 L1 里并排列出，每行带「区分证据」；
  • 新案例导入时，若库里已有同症状不同根因的案例而本案例没写「区分证据」，审核清单标黄提示（不阻断）；
  • 诊断时 L1 先给模型「候选原因 + 区分证据」，模型据此决定先取哪项证据，而不是看到一个相似案例就照搬处置。

4　读取机制

4.1 规则（写进知识库契约，替换现在「先整份读 RULES.md」那一段）

  1. 先看 L0：脚本输出的「客户知识库参照」第一段就是 L0；知识库里没登记的类型（如缺陷为 0）要如实说「本行未登记」，不要用通用知识冒充。
  2. 按 L1 选：先看候选原因与区分证据，决定要取哪项证据、引用哪几条；不要整个专题全读（--all 只在用户要「全部列出来」时用）。
  3. 引用前读 L2：处置步骤、审批要求、受影响版本、基线数值，必须出自 show 过的条目；L1 摘要只能用来说「有一条相关规定 / 一单类似案例」。每次回答最多 5 条。
  4. L3 只在四种情况读（见上图）。冲突时两边并列呈现、附原文，交用户裁决；默认采信顺序：修正 > 规范 > 本环境版本的缺陷与例外 > 手册 > 已确认案例 > 产品文档 > 其余。
  5. 适用性：条目与本实例画像的产品系列、版本、部署形态不符时，写「不适用本环境」，不得当作依据；没有画像时写「适用性未知」。
  6. 标蓝（v1.4.0 已做）：出自知识库的内容照旧标蓝，前面加类型名，如「〔手册 RB-LCK-001〕」。

4.2 为什么这样分工

做法原因
L0 / L1 由脚本附带「每次诊断先读」如果只写在提示词里，模型会漏；现在 9 个诊断技能的脚本本来就在输出里附知识库一节，把它改成 L0 + L1 是零额外调用，而且可以断言模型「看到了」。
L2 / L3 用命令取而不是读文件命令能保证一次只取一条、有长度上限、自动去掉废止条款和敏感内容；读文件会整份进上下文。命令行权限里技能脚本本来就放行，不用改权限。
L0 / L1 生成、不手写人只维护 L2；L0/L1 由元数据生成，永远和条目一致，不会出现「索引里有、条目已删」。
大小上限L0 ≤ 3 KB、单个专题 ≤ 6 KB、单条 ≤ 8 KB：知识库从几十条长到几千条，进上下文的量基本不变；超出时按「已确认优先、近期优先、案例支持数」截断并提示 --all。

5　导入怎么变

9　风险

风险应对
模型把类型判错人确认清单里逐条显示类型，可整批改；按类型校验必填要点，判错的条目往往缺要点，会被拦下；导入后可 retype。
导入变慢、要填的东西变多所有类型只有「类型、摘要、专题、出处」是硬性的；类型要点缺失多数只告警。画像由脚本起草。
模型不按层读，直接读文件L0/L1 由脚本附带，不依赖自觉；契约写明引用前必须 show；评测统计 L2 读取次数与知识库字数，回归时看得见。
适用性判断出错（画像写错、版本格式不一）只降权、不丢弃，并写明「不适用 / 未知」的理由；版本统一成可比较的格式，解析不了按「未知」。
画像里写进敏感信息校验拦截 IP、主机名、端口、口令样式；画像只记连接别名。
与 v1.4.0 已交付知识库的兼容不迁移也能用；迁移可重复执行；兼容清单保留一个版本。

10　待确认

  1. 一个条目一个主类型，还是允许多类型？ 建议一个主类型，混合内容拆条；多类型会让必填要点无法校验。
  2. 类型由目录决定，还是只是一个字段？ 建议目录 + 字段双写并校验一致：目录便于浏览与检索范围控制，字段让条目复制到别处也能自我说明。
  3. 环境画像怎么来？ 建议脚本只读起草 + 管理员补全确认；纯手写也可以，但版本、部署形态容易写错。
  4. 指标基线只并列展示，还是允许替换技能的阈值？ 建议只并列展示，保持「判定以脚本为准」的契约；替换阈值另立需求。
  5. 专题清单：建议先用上面 12 个，客户可增改；还是由你们先给一份？
  6. 旧清单 RULES.md / CASES.md：建议保留一个版本再删，还是这一版直接下线？
  7. 版本号：条目结构有变，建议容器版 v1.5.0、主干 skills-v13。
