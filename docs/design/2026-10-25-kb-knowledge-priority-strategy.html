2 · 四级优先级

为什么是这个顺序

  • 脚本判定最硬:它基于实测数据与确定性规则,可复现、可审计。知识库管的是「客户怎么说、以前怎么处置」,管不着「技能怎么工作」。
  • 客户知识高于官方文档:客户的规范是在官方行为之上的「本行约束」(变更窗口、审批、阈值),官方文档只说明产品默认怎么工作。 例如产品提供 pg_terminate_backend 终止会话,而本行规范规定「数据库侧不 kill 业务会话,交应用方处理」——两者都对,但执行时以本行为准。
  • 官方文档高于模型记忆:模型的训练数据混着 openGauss、PostgreSQL 与各版本 GaussDB 的说法,版本口径不可控; 官方文档集有明确的产品系列与版本,并逐条对本实例画像判断适用性。
  • 模型自带知识兜底:知识库覆盖不到的地方(本行无先例、官方文档没写)仍要给出可用的建议,但必须如实声明来源。
级来源能做什么不能做什么由谁保证
①skill 的 SKILL.md、references/ 方法论、脚本的确定性判定决定「发现了什么问题」「严重程度」—代码
②客户知识库(规范 / 修正 / 案例 / 本行历史路径 / 手册 / 缺陷 / 基线 / 画像 / Wiki / 客户摘录的产品文档)处置建议的首选依据:措辞、步骤、变更窗口、审批都按客户的来;有手册先给手册 不能补报脚本没报的违规,不能抹掉脚本报了的,不改 severity;库内:修正 > 条款 > 其余提示词 + 代码(检索排序)
③官方文档集(G25132C,6,023 条)说明产品怎么工作:参数含义与默认值、视图字段、错误码、官方排障思路 与客户规范、案例不一致时不得覆盖,只能并列呈现交用户裁决;「不适用本环境」的不得作为依据代码(单独候选池、排在客户之后)+ L0 提示
④模型自带知识知识库「无对应条款 / 无相似案例」时给出通用做法、补充解释与分析 不得冒充客户规范或案例;绝不允许编一条客户规范或案例;不标蓝提示词 + cite-check

3 · 检索关:什么知识能进上下文 代码

模型只能用「看得见」的知识。检索关决定看得见什么——这是整套策略里最硬的一环,完全由代码执行。

相关度门槛(过不了就写「无」,不硬凑)

门槛数值作用
向量相似度直通vector_min = 0.45语义足够像,直接算相关
词法原始分下限lexical_min = 0.01防「排第一但其实不相关」
强 token + 覆盖强 token ≥ 1,且命中 ≥ 2 个查询词或覆盖率 ≥ 0.12强 token = 标识符(带 _ . :)、≥6 字符的词、连成 ≥4 字的中文短语;泛词(wait / lock / stat…)不算
相对门槛relative_floor = 0.45词法分低于本池同类最高分的 45%、向量又不够像的,剔除
分类型门槛(RRF 归一分)条款 / 案例 / 路径 0.25,其余 0.20低于门槛整类返回「无」
短问题放宽(仅纯问答)≤ 3 个词且全部命中「死锁」「连接数」这类短问题能查到;诊断发现生成的长查询不放宽

数值来自 common/kb/config.py 的 Thresholds,可在 kb.yaml 的 thresholds 下按客户调整;图检索另有 3 秒时间预算,超时就不走路径、照常出结果。

4 · 适用性与可信度:代码打标签,模型按标签用

测试开关(仅测试环境):测试库画像是 openGauss 5.0.3,而官方文档集是 GaussDB 505.2——按规则全部「不适用」,测不出官方文档的作用。 所以测试期间在 kb.yaml 打开 test_switches.docset_applicability_unknown,官方文档一律按「未知」处理;health 每次提示、L0 里写明, 打标准知识库包时开关开着会被拒绝,带不进正式版本。

可信度标签(引用时必须带上)

知识标签模型怎么用
案例结论强度:已确认 / 推测 / 待验证非「已确认」的引用时带上标签;依据它给高风险操作建议前要读 L3 原文
Wiki 经验已验证 / 未验证 / 已过时同上;「已过时」的不作为依据
已知缺陷厂商结论:已确认 / 待确认如实转述;受不受影响以「本环境 X 受影响 / 不受影响」为准

官方文档的摘要脚本摘要 / 「摘要由模型依据原页撰写(脚本已核对其中的参数名、数值都出自原页)」摘要只用来决定读不读;具体数值、步骤以 show 读到的原文为准

5 · 生成关:模型怎么用这些知识 提示词

这一关写在「知识库契约」里(注入 health / lockwait / waitevent / vacuum / wdr / memanalyze / sqltune / proctune / sqlreview 9 个诊断 skill 的固定标记区), 纯问答的规则在 AGENTS.md 与 gaussdb-kb 的 SKILL.md。

5.1 按层读:看得越深,用得越准

5.2 写法规则

情形必须怎么写
引用客户知识库带类型与 ID 与出处(〔规范 GS-…〕〔案例 S2-…〕〔手册 RB-…〕);整句包进 <font color=#2f6fdb>…</font> 显示为蓝字。 一个标签只包一句 / 一个列表项 / 一个表格单元格;标签里不加粗、不放行内代码(会盖掉蓝色);代码块里不放标签
知识库没有对应内容如实说「本行无先例,以下为通用做法」,后面的内容不标蓝;绝不允许编一条客户规范或案例
某类为 0说「本行未登记」,不用通用知识冒充
知识库与脚本判定不一致两边并列呈现,交用户裁决;不选边、不假装一致;severity 以脚本为准
贵行基线只说明「这个数在本行平时是多少」,与脚本阈值并列,不改 severity
脚本结论、自己的分析、通用经验不标蓝;拿不准是否出自知识库的,不标
知识库未接入 / 目录不存在照常按 skill 自身知识作答,不提知识库、不说「查过知识库」

6 · 核对关:事后查有没有编 代码

kb.py cite-check --text "<回答>" 从回答里抽出所有知识 ID(规范 GS- / 案例 S1–S4- / 手册 RB- / 缺陷 KD- / 基线 BL- / 产品文档 PD-(含官方 PD-G25132C-NNNNN)/ Wiki WK- / 画像 EP-),逐个到库里核对:

结果含义处理
✓ 存在 / 前缀匹配库里有保留
⚠ 已废止条款在 archive/不得据此判定,改引现行条款
⚠ 不唯一前缀命中多条写全 ID
✗ 未找到疑似编造(退出码 2)从回答里删掉

其它「看得见」的防线:

  • 蓝字:用户一眼看出哪些话来自客户知识库;没有 ID 的蓝字本身就可疑。
  • 状态行:每节开头写明模式(向量 / 文件)、向量覆盖率、图来源;降级如实写,不藏。
  • 测试开关:L0、health 都提示;打包时拒绝。
  • 导入侧:模型精修的摘要,脚本逐个核对其中的参数名、视图名、等待事件名、数值都原样出自原页,对不上整条退回;validate 有错误、测试开关开着,都不许打包。
核对关管不到的:没标蓝、也没写「通用做法」的那些话,究竟是模型自带知识还是脚本结论——目前没有机器检查。见第 9 节。

7 · 冲突怎么处理

冲突谁说了算回答里怎么写
脚本判定 vs 知识库条款阈值判定与 severity 以脚本为准两边并列:「脚本按 X 判为 warn;贵行规范 GS-… 的阈值是 Y」,交用户裁决
客户规范 / 案例 vs 官方文档客户为准(本行约束在官方行为之上)先写客户的(蓝),再写官方的并注明「官方默认 / 官方说明」
修正(errata)vs 条款修正为准引修正,并说明它修正了哪条
两条知识说法冲突不自行裁决读 L3 原文核对后并列呈现
同一现象本行有过多种根因按「区分证据」取证后再选说明凭什么判断是这个根因,不照搬相似案例的处置
条目「不适用本环境」不作为依据最多一句「这是 openGauss / 其他版本的行为」
官方文档 vs 模型记忆官方文档为准(有明确版本)引官方条目 ID;模型记忆中的其它版本说法不写,或注明「其他版本」
知识库为空 / 无对应模型自带知识「本行无先例,以下为通用做法」

模型的回答(按来源着色)

脚本结论客户知识库官方文档(建议的标记)模型分析
锁等待一直报超时,根会话能不能直接 kill?lockwait_timeout 要不要调?

当前 3 个会话在等锁,最长 95 秒;根会话 pid 4211 处于 idle in transaction 已 14 分钟(脚本判定 LOCK_WAIT_LONG,critical)。

按贵行规范〔规范 GS-XACT-001〕,空闲事务一律经应用运维平台定位并由应用方处理,数据库侧不 kill 业务会话(出处:《运维规范》v5 §6.2)。

按处置手册〔手册 RB-LCK-001〕,先把根会话的 application_name / client_addr 交应用运维平台;超过 10 分钟未解除,值班经理审批后才可在数据库侧终止根会话(出处:CBST 运维手册 v3 §4.2)。

本行有过同类问题〔案例 S2-20250120-CBST-空闲事务持锁阻塞〕,根因是应用连接池归还连接时未提交事务(结论:已确认)。

官方文档〔产品文档 PD-G25132C-02895〕:lockwait_timeout 是单个锁的最长等待时间,默认 1200000 毫秒(20min),USERSET 类型;适用性未知(测试开关)。

分析:调小 lockwait_timeout 只会让等锁的会话更早报错,不会释放根会话持有的锁,不建议靠调参解决;根会话已超过 10 分钟,可以按手册走审批。

PD-0001 是 openGauss 的行为、不适用本环境,回答里没有用它。现状:客户知识库的句子是蓝字;官方文档的句子标不标蓝没有明确规定(上图青色是建议的单独标记,见第 9 节)。

9 · 现状缺口与改进建议

#缺口 缺口影响建议 建议
1第 4 级主要靠提示词约束:模型可能把自带知识混进来而不声明「通用做法」用户分不清一句话是脚本事实、客户知识还是模型说的;cite-check 只能查编造的 ID,查不了「未声明的自带知识」 加一道生成后检查:回答里出现具体参数值、阈值、命令、操作步骤,却既无知识库引用、也无「通用做法」声明的,提示补来源或改为声明
2官方文档的位置没写进契约:「以客户为准」只写在导入说明与 L0 里;标蓝规则没说官方文档标不标模型可能把官方文档也标成蓝字,用户把「官方说法」当成「本行规定」 契约补第 3 级;官方文档用单独的标记(如青色或〔官方〕前缀),与客户知识区分开
3兜底声明两种说法:AGENTS.md「以下内容未在本地规范文档中找到,仅供参考」vs 契约「本行无先例,以下为通用做法」回答风格不一致,也不便于机器检查 统一成一种,并与需求 3 合并:标明「由大模型生成,需结合业务情况评估」
4信息不足时不乱答(需求 3)尚未落地知识库与脚本都没覆盖时,模型仍可能给出看似确定的结论 契约加「信息不足判定」:缺关键证据时先说缺什么、要什么数据,不给确定结论
5内核调整的证据门槛(需求 1)尚未落地sqltune、健康检查等可能建议改内核参数,而证据不足 脚本侧加证据门槛:只有指定指标越线(并附数值)时才允许出现内核参数建议;否则只给 SQL / 应用层建议
6证据链(需求 2):诊断结论到知识库原文的链接用户要逐条点开核对比较麻烦 引用时附可点的大盘直达链接(大盘「目录」页签已支持 #outline=I:<ID> 定位到 L2、再点到 L3)
建议的落地顺序:① 契约统一(第 2、3 条)+ 官方单独标记 → ② 信息不足约束与「大模型生成」标注(需求 3)→ ③ 生成后来源检查(第 1 条)→ ④ 内核调整证据门槛(需求 1)→ ⑤ 证据链直达链接(需求 2)。前两步只改契约与 SKILL.md,约 1 天;后三步各需脚本改动与回归。
