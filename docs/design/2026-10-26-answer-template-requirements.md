- 发起:2026-10-26,客户演示之后
- 目标:智能体的回答内容模板化 —— 同一类问题,回答的结构、顺序、措辞口径固定下来
- 分工:需求由用户定,这里逐条记录;全部记完、用户确认后再出实现方案,之后才改代码
- 进度:R1–R7 全部确认(D1–D20),2026-10-26 开始实现。R1–R4 已确认。待确认的 15 个问题,用户答复前 6 个(D1–D6),其余由用户授权「都听你的建议」,按记录人的建议定(D7–D16)。R5、R6 已记录,待确认都附了建议

## 一、模板总览(实现时以这一节为准)

### 1. 所有回答共用的骨架

| 位置 | 内容 | 来源 |
|---|---|---|
| 第一行(只在问的是某个时间段时) | 评估时段:要的是哪段、实际评估的是哪段、为什么 | 现行规矩,D7 |
| 抬头 | 总体状态带:级别(以脚本判定为准)+ 驱动一句 + 判断校验 | D4 |
| 抬头之后 | 短结论:2–4 句,开发人员也看得懂 | D5 |
| 正文 | 按问题类型分段(见下表);每段先「应用视角」、再「数据库机制」 | R2、D2 |
| 正文里 | 用到的知识直接融进正文,不特意声明来源;该句用特殊颜色,句后「(引用自 xxx 知识库)」 | R5 |
| ~~总结末尾~~ | ~~「引用的知识」~~:按 R5 建议去掉(待确认 R5-3) | D8 → R5 |
| 最后 | 1–3 条「需要就 xxx 展开说明吗?」 | D6 |

### 2. 正文按问题类型分段

| 问题类型 | 怎么判定 | 正文各段 |
|---|---|---|
| 健康检查(R1) | 用户要巡检 / 体检(此刻或某个时间段) | ① 现象(多维度)② 根因和证据链 ③ 解决方案(按优先级)④ 总结和结论 |
| 故障排查(R3) | 用户描述一个现象或告警(慢、超时、锁等待多、连接满、膨胀、某个告警……),不管落到哪个技能 | ① 现象(报的那个 + 关联现象)② 根因(证据链)③ 解决方案(按优先级)④ 总结 |
| SQL 性能优化(R4) | 用户要优化某条 SQL,或问某条 SQL 为什么慢 | ① 现状分析(耗时与趋势)② SQL 文本和执行计划解读 ③ 怎么优化(前后对比)④ 总结 |
| 知识问答(R6) | 问知识本身(规范、参数、错误码、视图字段、功能、做法),不要求查某个实例 | 开头「解答来源:……」→ ① 解答正文 ② 举例说明(场景、关联影响和效果)③ 引申和拓展 + 反问 |

知识问答不用第 1 节的总体状态带(没有严重级别),知识引用的写法也和排查类不同:来源写在最开头(R6),不是只在句后括号里(R5)。

判定有重叠时:点名要健康检查的按 R1;点名优化某条 SQL 的按 R4;其余描述现象或告警的按 R3(D9)。
只要求看执行计划、不要优化的,只写 R4 第 ② 段,不硬凑另外几段(D13)。

### 3. 两种读者(R2)

每一段分两小段写,不割裂:
- **应用视角**(开发人员能看懂):对业务、接口、交易有什么影响,应用里哪类写法会导致它。
- **数据库机制**(给数据库工程师):接着同一件事、同一批对象(同一条 SQL、同一张表、同一组会话)往下讲「为什么会这样」—— 锁、MVCC、WAL、执行计划、参数怎么起作用。

## 二、需求清单

每条分三栏:「原话」照录用户说的;「理解」是记录人的转述;「状态」= 已记录 / 已确认 / 已实现。理解与原话有出入时以原话为准。

### R1 健康检查的回答按四段式组织(2026-10-26)

- **原话**:健康检查按照:1. 现象:多维度现象分析 2. 根因和证据链:对每个现象进行分析和根因排查,并且给出证据链 3. 解决方案,按照优先级列出最优先解决的问题,次优先解决问题等,以及详细优化方案 4. 总结和结论,给出总结,和建议,甚至可以向用户提需求。
- **理解**:健康检查(gaussdb-health)的回答固定为四段,顺序不变:
  1. **现象**:从多个维度把看到的现象摆出来(各维度发现了什么、数字是多少)。
  2. **根因和证据链**:对**每一个**现象逐个分析、排查根因,给出从现象到根因的证据链(每一环都对应采集到的数据)。
  3. **解决方案**:按优先级排列 —— 最优先解决的问题、次优先的……;每个问题带详细的优化方案。
  4. **总结和结论**:总结 + 建议;可以向用户提需求,形式可以是「需要就 xxx 展开说明吗?」(D6)。
  - 此刻巡检与时段体检都用四段式(D3);四段之前是总体状态带(不变,D4)和短结论(D5)。
- **状态**:已确认

### R2 回答同时照顾开发人员和数据库工程师两种读者(2026-10-26)

- **原话**:回答内容上要同时兼顾开发人员(对数据库不是特别懂,更多的站在应用的视角给出说明)和数据库工程师(对数据库原理和内核很了解,可以在机制上进行更深入说明)这两种角色,特别是第一种角色也要能看的懂,多使用应用视角来解释数据库的问题。
- **理解**:
  - **开发人员**(对数据库不太懂):站在应用的视角说明问题;**底线是这类读者也要能看懂**,数据库问题尽量用应用视角来解释。
  - **数据库工程师**(懂原理和内核):在机制上深入说明。
  - **适用范围**:健康检查、Top SQL、WDR、SQL 调优、知识库问答(D1),故障排查也一样(D16)—— 即所有回答。
  - **写法**:分两段,先应用视角、再数据库机制,但不能割裂(D2,见模板总览第 3 节)。
- **状态**:已确认

### R3 故障排查的回答按四段式组织,从一个现象扩到关联现象(2026-10-26)

- **原话**:故障排查按照:1. 现象:用户或报警只看到其中一个现象,把关联现象也都分析出来。2. 根因:证据链和根因分析 3. 解决方案 4. 总结
- **理解**:用户带着一个具体问题来问(「交易超时」「锁等待多」「某条 SQL 变慢」「收到某个告警」)时,回答固定为四段:
  1. **现象**:用户或告警往往只看到其中一个现象;回答要从这个现象出发,把与它**关联的其它现象**也分析出来。例如用户只说「交易超时」,要一并看锁等待、阻塞链、长事务 / 空闲事务、等待事件、死元组膨胀。
  2. **根因**:证据链 + 根因分析(每一环落到采集到的数据上)。
  3. **解决方案**:按优先级排、带详细方案(D11)。
  4. **总结**:同 R1 第 4 段(D11)。
  - 范围按问题分,不按技能分(D9);关联现象怎么找见 D10。
- **状态**:已确认

### R4 SQL 性能优化的回答按三段式组织(2026-10-26)

- **原话**:sql性能优化:1. sql当前现状分析,平均时间,最大时间等等,包括这个sql的性能变化趋势,是否在哪个时间段突然变慢,最近这段时间的性能变化等等 2. sql文本和执行计划解读,慢在哪里 3. sql如何优化,怎么改,优化前后文本和执行计划的差异,以及cost和执行耗时的变化
- **理解**:对某一条 SQL 做性能优化时,回答固定为三段,另加一段总结(D12):
  1. **现状分析**:执行次数、平均耗时、最大耗时等;**性能变化趋势**:有没有在某个时间段突然变慢,最近一段时间是变好还是变坏;突然变慢的,同时核对那时执行计划变没变(D14)。
  2. **SQL 文本和执行计划解读**:把 SQL 和执行计划讲清楚,指出**慢在哪里**。
  3. **怎么优化**:怎么改;**优化前后对比** —— SQL 文本差异、执行计划差异、cost 变化、执行耗时变化(耗时的口径见 D15)。
  4. **总结**(D12)。
  - 适用:优化某条 SQL、问某条 SQL 为什么慢(含从 Top SQL、慢 SQL、WDR 点进来的);只看执行计划的只写第 2 段(D13)。
- **状态**:已确认

### R5 排查类回答用到知识库时:不特意声明来源,用特殊颜色标出,句后括号注明引用自哪个知识库(2026-10-26)

- **原话**:另外如果排查问题类的问题应用到知识库,不要特意标注来源于知识库,用特殊颜色标记,并在后面用()标注引用自xxx知识库。
- **理解**:
  - 回答里用到知识库的内容,**直接融进正文**,不写「根据知识库检索……」「知识库显示……」这类专门交代来源的话,也不单列一节「客户知识库参照」。
  - 出自知识库的那句话**用特殊颜色**标出来(模型自己的分析、通用经验不上色,现行规矩不变)。
  - 这句话后面用括号注明出处:**「(引用自 xxx 知识库)」**。
  - 适用范围:排查问题类的回答(健康检查 R1、故障排查 R3、SQL 优化 R4);知识库问答是否同样处理见待确认 R5-4。
- **状态**:已记录

### R6 知识问答的回答按三段式组织,开头先标注解答来源(2026-10-26)

- **原话**:知识问答:有专门的知识问答类问题,1. 解答正文,这部分和故障类问题不一样,要最开始标注出解答正文的来源。2. 对问题进行举例说明,客户问的这个问题一般会出现在哪些应用场景,会有哪些关联影响和效果 3. 对问题的引申和拓展,并反问用户是否想了解关联内容等等
- **理解**:专门问知识的问题(问规范、参数、错误码、视图字段、产品功能、概念、做法,不要求诊断某个实例),回答固定为三段:
  1. **解答正文**:与排查类(R5)相反,**一开始就标注出解答正文的来源**(出自哪个知识库、哪一条),然后给出解答。
  2. **举例说明**:这个问题一般出现在哪些应用场景;会带来哪些关联影响、起什么效果。
  3. **引申和拓展**:往相关内容延伸,并**反问用户**是否想了解关联内容(与 D6 的「需要就 xxx 展开说明吗」同一种形式)。
- **状态**:已记录

R6 待确认(括号里是记录人的建议,用户不另说就按建议执行):

1. **怎么算「知识问答」**:(建议:问的是知识本身、不要求查某个实例的就算,例如「lockwait_timeout 默认是多少」「GAUSS-10512 是什么意思」「PG_LOCKS 的 granted 是什么」「Plan Hint 怎么写」「我们行 DDL 变更有什么规定」。问题里既要查实例又要结合知识的,例如「og5 现在有没有锁等待,结合知识库给建议」,按故障排查 R3。)
2. **开头的来源怎么写**:(建议:第一行「解答来源:」后列出用到的每一条,写法同 R5-1 的类别 + 编号,例如「解答来源:GaussDB 官方文档 PD-G25132C-02895;贵行运维规范 GS-CHG-003」。客户知识与官方文档说法不一致时,开头就写明「以贵行规范为准」。)
3. **知识库里没有怎么办**:(建议:开头写「解答来源:知识库中未找到相关内容,以下为通用知识,仅供参考」,正文不上色。同时把现在两种兜底说法 —— AGENTS.md 的「以下内容未在本地规范文档中找到,仅供参考」和契约里的「本行无先例,以下为通用做法」—— 统一成这一种。)
4. **正文里还上不上色、加不加括号**:(建议:出自知识库的句子仍上色,便于和模型自己的组织说明区分;只用到一条知识时不再逐句加括号,开头已写明;用到多条时,句后括号只写编号,对应到开头的来源。)
5. **第 2 段的场景从哪来**:(建议:优先用知识库里贵行自己的案例 —— 「贵行出现过:……」,上色并注明编号;没有本行案例时用通用场景,不上色,写明是通用场景。不编造「贵行出现过」。)
6. **两种读者(R2)怎么落**:(建议:第 1 段写直接答案 + 机制说明(给数据库工程师);第 2 段的应用场景本身就是应用视角(给开发人员)。不再在每段里各拆两小段。)
7. **开头放不放总体状态带和短结论**:(建议:知识问答没有严重级别,不放总体状态带;第 1 段第一句就是直接答案,起短结论的作用。)

## 四、可行性(记录时核对现有能力发现的,实现方案里展开)

- **R4 第 1 段(现状与趋势)现在没有**:gaussdb-sqltune 的报告从「被分析的 SQL」开始,没有执行次数、平均 / 最大耗时与趋势。数据库里有三处来源:累计语句统计(dbe_perf.statement)、逐次执行记录(statement_history,保留期由参数决定)、WDR 快照里按快照间隔记的语句统计(snap_summary_statement,能拉出按天 / 按小时的趋势)。现有白名单脚本能不能按 sql_id 取这几样要逐个核对;要新增脚本的话,客户需要重新登记白名单。
- **R4 第 3 段「优化后的执行耗时」在客户环境量不到**:经中间件取计划时 ANALYZE 固定关闭(客户只读要求),计划里的行数和耗时都是规划器估算;假设索引验证在客户环境也不可用。所以优化前的耗时有实测(语句统计),优化后只有 cost 估算。
- **优化前后执行计划对比**:改写方案经 verify 取得了改写后的计划,可以并排对比;只建索引的方案在没有假设索引的环境里拿不到「建索引后的计划」,要写明。
- **R3 的关联现象清单**(D10)要新写,并接进各技能的说明;加跑技能会让回答变慢,实现后要实测耗时。
- **R5 的引用写法改了,牵动四处**:注入 9 个诊断技能的知识引用契约(现在规定写〔类型 ID〕、蓝字)、AGENTS.md、cite-check 从回答里认 ID 的规则、各技能脚本输出的「客户知识库参照」小节(它是给模型读的输入,可以保留,但要说明回答里不照搬成一节)。另外《前端对接接口说明》(公共仓库 gh_gs_k8s_agent)写了回答里蓝字的标记方式,客户前端按它渲染;颜色或标记方式变了要同步改,并通知客户。

## 五、与现有规则的关系

现行健康检查的版式(skills/gaussdb-health/SKILL.md 第 6 步「报告」):抬头状态带 → 维度概览矩阵 → 按严重度排序的发现(每条:证据 → 根因 → 建议)→ 关键原始证据 → 处置优先级 P0/P1/P2 → 收尾一句。与 R1 的对应:

| 现行内容 | R1 里的位置 |
|---|---|
| 抬头状态带、判断校验徽章 | 最前面,不变(D4) |
| (新增)短结论 | 抬头状态带之后(D5) |
| 维度概览矩阵 | ① 现象 |
| 发现里的「证据 → 根因」、关键原始证据 | ② 根因和证据链(证据串成链,原始表作为链上的证据) |
| 发现里的「建议」+ 处置优先级 P0/P1/P2 | ③ 解决方案(「最优先 / 次优先」沿用 P0/P1/P2,每条带风险级与「需人工执行」) |
| 收尾一句 | ④ 总结和结论 |

现行 SQL 调优的版式(skills/gaussdb-sqltune/SKILL.md 第 8 步「报告」):被分析的 SQL → 执行计划(瓶颈节点标 [P1]…)→ 计划走查 → 证据链摘要 → 根因 → 已验证推荐 → 未验证想法 → 风险。与 R4 的对应:

| 现行内容 | R4 里的位置 |
|---|---|
| (新增)执行次数、平均 / 最大耗时、趋势、计划变没变 | ① 现状分析 |
| 被分析的 SQL、执行计划、计划走查、根因、证据链摘要 | ② 解读 |
| 已验证推荐(补文本差异、计划差异、耗时口径)、风险、未验证想法 | ③ 怎么优化 |
| (新增)总结 | ④ 总结 |

需要保留、不因模板化而改变的现行规矩:

- **严重级别以脚本判定为准**:总体状态等于脚本判定的最重一条,短结论和总结里都不能下调,也不能补报脚本没报的问题。
- **每条结论必须引用一个真实数字**:没有数据支撑的进「未证实想法」,不进正式发现。证据链的每一环同样要落到采集到的数据上。
- **报告只呈现结论,不呈现推演**:证据链是「数据 → 结论」的链条,不是模型自我纠正的过程。
- **行动项必须自带结论正文**:解决方案里不能只留一个指针(例如只写「落实 sqltune 结论」)。
- **知识引用规矩**(按 R5 调整写法):出自知识库的句子上色、句后括号注明出处;模型自带的通用知识不上色,仍要声明为通用做法(这一条不算「特意标注来源于知识库」,是在说明这句**不是**出自知识库)。引用前先读原文(show)再写、不适用本环境的条目不作依据,这两条不变。
- **内核调整要有证据**(此前提的需求 1):R2 允许给数据库工程师讲机制,但讲机制不等于可以没有证据就提内核参数调整。
- **关联现象也要有数据**(R3):第 ① 段列出的关联现象,要么来自这次采集到的数据,要么明确写「未采集 / 采集不到」,不能凭经验写「通常还会伴随……」冒充本次的现象。
- **回看不了的现象要说清楚**(R3):问的是过去的时间段时,事后看不到的现象(例如当时的阻塞链)照常说明「这一项回看不了」,不拿现在的状态冒充当时。
- **「展开说明」的提议不能替代正文**(D6):四段里该写的结论、证据、方案不能省掉、留到「需要再展开」。
- **只推荐验证过的方案**(R4):第 ③ 段的「怎么改」只放验证通过的索引 / 改写;cost 前后数字照抄验证结果,不自己算倍数。
- **估算和实测分开写**(R4、D15):实测的写实测,估算的标「估算」,不能写成实测。

## 七、实现记录(2026-10-26)

与方案(2026-10-26-answer-template-plan.html)不同、实现时调整的几处:

- **慢 SQL 用榜单格式**,不用故障排查四段:「最近有哪些慢 SQL」是列排名,套排查四段很别扭。故障排查四段用于锁等待、等待事件、vacuum、内存四个技能与跨技能的现象提问。

- **逐次执行记录按小时取**(`sqltune.exec_history`):方案写的「最近 200 次执行」对高频语句只覆盖几分钟,改成近 7 天每小时一行,计划只在变化时给全文(og5 实测 0.34 秒)。
