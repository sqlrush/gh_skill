# 一次调用的全过程：逻辑名 → id → 执行

skill 代码里写的是**逻辑名**（`topsql.top_sql`），而客户 GRMP 的执行接口
**只认数字 id**。这份文档说明中间那层转换发生在哪、怎么发生的。

下面的报文全部来自一次真实调用（`grmp_middleware/` 抓的），不是构造的样例。

---

## 全景

```
 skill              client.py                      客户 GRMP
   │                    │                              │
   │ run("topsql.       │                              │
   │     top_sql",…)    │                              │
   ├───────────────────▶│                              │
   │                    │  ① POST common-operations    │
   │                    │     {dataIp, offset, limit}  │
   │                    ├─────────────────────────────▶│
   │                    │◀─────────────────────────────┤
   │                    │     result.list[89]          │   ← 含 cmd_name + id
   │                    │                              │
   │                    │  ② 建字典 {cmd_name: id}      │
   │                    │     ┄ 内存，进程内复用 ┄       │
   │                    │                              │
   │                    │  ③ "topsql.top_sql" → "76"   │
   │                    │                              │
   │                    │  ④ POST invoke               │
   │                    │     {dataIp, id:"76", param} │
   │                    ├─────────────────────────────▶│
   │                    │◀─────────────────────────────┤
   │◀───────────────────┤     status:finished          │
   │  全字符串的行字典    │     result.data[]            │
```

**一次调用 = 2 次 HTTP**（首次）。之后同进程再调别的脚本只剩接口二那一次
—— 清单缓存住了。实测日志比例约 20 次清单 : 77 次执行。

转换全部发生在 `common/grmp/client.py` 一个文件里。skill 从头到尾不知道
id 是什么。

---

## ① 调接口一，拿全量清单

接口一是「把这个实例下的**所有**命令列出来」，**不接受按名查询**。

```
POST /icbc/paas/aiops/grmp/diagnostic/agent/common-operations
auth: <令牌>
```

请求体 —— 注意没有 `cmd_name`：

```json
{ "dataIp": "10.0.0.9", "offset": 1, "limit": 1000 }
```

响应体：

```
code = "0"    msg = "success"
result = PageInfo（18 个字段），total = 89
```

`result` **不是数组**，是 MyBatis 的分页对象。真正的清单在 `result.list`：

```json
{
  "id":          "1",
  "cmd":         "EXPLAIN (ANALYZE false, BUFFERS false, FORMAT TEXT) {{sql}}\n",
  "cmd_name":    "explain.plan_text",
  "description": "explain.plan_text",
  "cmd_type":    "SQL",
  "param":       [ { "param_name": "sql", "data_type": "String", ... } ]
}
```

**逻辑名就是 `cmd_name`**，它和 `id` 在同一条记录里 —— 映射关系由客户接口
提供，我们不维护任何映射表。

---

## ② 本地建映射（内存，不落盘）

`common/grmp/client.py`

```python
def _id_map(self):
    if self._ids is None:                       # 只建一次
        self._ids = {
            d.get("cmd_name"): d.get("id")      # ★ 关联就是这一行
            for d in self.list_operations()
            if d.get("cmd_name")
        }
    return self._ids
```

建出来的字典：

```
┌──────────────────────────────┬──────┐
│ cmd_name                     │  id  │
├──────────────────────────────┼──────┤
│ explain.plan_text            │  "1" │
│ explain.plan_text_analyze    │  "2" │
│ health.archive_mode          │  "3" │
│ …                            │   …  │
│ topsql.top_sql               │ "76" │
│ …                            │   …  │
└──────────────────────────────┴──────┘
                                  89 条
```

---

## ③ 查字典换出 id

```python
def resolve_id(self, script_name):
    ids = self._id_map()
    if script_name not in ids:
        raise GrmpError("中间件未注册脚本 %s。已注册的有：%s" % ...)
    return ids[script_name]
```

```
"topsql.top_sql"  ──查表──▶  "76"
```

找不到就报错并**列出全部已注册脚本名** —— 不猜、不回退。这样能一眼看出
是发布 DML 没灌全，还是脚本名写错了。

---

## ④ 调接口二，按 id 执行

```
POST .../common-operations/invoke
```

请求体 —— **逻辑名已经消失，只剩 id**：

```json
{
  "dataIp": "10.0.0.9",
  "id": "76",
  "param": [
    { "param_name": "order", "param_value": "n_calls" },
    { "param_name": "limit", "param_value": "2" }
  ]
}
```

响应体 —— 注意**信封变了**：没有 `code`/`msg`，改用 `status`：

```json
{
  "result": { "type": "array", "data": [
      { "unique_sql_id": "4238204932", "query": "DROP SCHEMA ...",
        "calls": "1", "total_sec": "0.01", "avg_ms": "6.63", "rows": "0" }
  ]},
  "task_id":   "grmp-59a2aa9f-…",
  "call_type": "sync",
  "status":    "finished"
}
```

两个接口的响应信封不同，是客户接口的既有事实，不是我们的设计。

---

## ⑤ 回到 skill

```python
rows = [
  {"unique_sql_id": "4238204932", "query": "DROP SCHEMA ...",
   "calls": "1", "total_sec": "0.01", "avg_ms": "6.63", "rows": "0"},
]
```

**所有值都是字符串** —— `calls` 是 `"1"` 不是 `1`。这就是
`common/grmp/values.py` 存在的理由：

```python
bool("f")        -> True      # 布尔列取回来是 'f'，判断结果正好相反
int("3704.0")    -> ValueError # relpages 是 double precision
x is None        -> 永远为假    # NULL 渲染成空串
```

直连路径**刻意产出同样的形状**（不返回原生 int/bool）—— 本地若能拿到原生
类型，本地写出的解析代码到客户环境会全部失效。

---

## 实测：接口二只认 id

| 试法 | 结果 |
|---|---|
| `{"id": "3"}` | ✅ `status: finished`，返回数据 |
| `{"id": "health.archive_mode"}` | ❌ `脚本 id=health.archive_mode 不存在` |
| `{"cmd_name": "health.archive_mode"}` | ❌ `请求体含不支持的字段：cmd_name` |

第三种情况值得单独说：**多传一个字段是直接报错，不是被忽略**。如果未知字段
被静默丢掉，调用方会以为自己传的参数生效了，而实际没有 —— 这类「以为传了、
其实没传」比报错难查得多。

---

## 三个设计要点

### 为什么不硬编码 id

客户接口文档里 `id=56` 是「查看数据库信息」，而调用示例里同一个 `id=56`
被传了慢 SQL 的参数。**id 是环境相关数据，不是稳定契约。**

硬编码的失败方式极其隐蔽：换环境后 id 依然存在、指向另一条脚本、
执行成功、结果无关、**不报错**。

已实测验证：把本地 89 条脚本的 id 整体 +1000，skill 取回的结果完全不变
（`grmp_middleware/` 下的探针）。

### 缓存的边界

清单缓存在**进程内**。客户若在进程运行期间重新发布脚本，缓存会过期。
留了 `invalidate_cache()` 手动失效，但**没有自动检测** —— 长驻进程要注意。

### ⚠️ 一个未证实的前提

`{cmd_name: id}` 这个字典假设 **cmd_name 唯一**。

客户那边是否唯一**未确认**。而他们的 `script_config` 有 7 个作用域列
（`region` / `deployment_form` / `execute_node_type` / `cluster_deployment_mode` /
`kernel_version` / `compliance_mode` / `refered_appbusiness`）我们完全没参与
过滤 —— 很可能他们就是靠那些列区分同名脚本的（比如同一个 `health.overview`
在集中式和分布式下是两条不同的 SQL）。**那样重名是正常设计，不是异常。**

若真重名，上面那行字典推导会**后者覆盖前者**，静默指向另一条脚本。

交付前应向客户确认两件事：

1. `script_config.script_name` 有没有唯一约束？
2. 同一个 `dataIp` 下，接口一返回的 `cmd_name` 会不会重复？

第 2 条若成立，解析逻辑要改：不能只按 `cmd_name` 建字典，得连作用域一起匹配。
