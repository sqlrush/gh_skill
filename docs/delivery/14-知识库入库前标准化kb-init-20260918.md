# 知识库入库前标准化：gaussdb-kb-init（2026-09-18，skills-v12.13 / agent-v0.6）

## 为什么要有它

客户手里的工单材料形态很杂：华为的问题分析报告（docx）、ITSM 导出（xlsx/csv）、微信里转来的截图、随手记的 txt。
知识库导入（`gaussdb-kb` 的 ingest → propose → 选择列表 → apply）吃的是结构化材料，直接喂杂格式，
要么脚本拒绝（照片、扫描件），要么模型在导入环节同时做「读懂」和「抽取」两件事，出错了分不清是哪一步。

`gaussdb-kb-init` 把「读懂并拉平成同一种格式」单独拎出来，作为**入库之前的标准化步骤**：

```
客户材料（docx / pdf / txt / md / csv / xlsx / 照片）
      │  gaussdb-kb-init:scan → 模型写草稿（照片用 read 看图）→ render
      ▼
统一格式 md（六要素:时间、系统、现场、判断、处置、复发标志）   ← 标准化文档,可复核、可归档
      │  gaussdb-kb（导入）:ingest → propose → 选择列表 → apply
      ▼
知识库（md 文件 + 向量库 + 图库）
```

## 统一格式

一单一份 md，frontmatter 放 `occurred_at`（时间）/ `system`（系统）与出处，正文固定四段
`## 现场 / ## 判断 / ## 处置 / ## 复发标志`。段名与知识库 `cases/` 的案例格式一致，所以标准化之后
导入流程一个字不用改。完整字段见 `skills/gaussdb-kb-init/references/std-format.md`。

三条硬规矩，都是防静默失效的：

1. **六要素缺一不可**。原文真没写，要显式写「原文未写明」——空着、`无`、`TODO`、`?` 一律被脚本拒绝。
   空白到了下游会被读成「没这回事」，而不是「没查到」。
2. **照片抽出来的内容标 `extracted_by: model`**。它没有可 diff 的原文，复核成本和脚本抽的不一样，文件里必须看得出来。
3. **日期认不出来就报错，不猜**。猜错日期会让案例挂到错的时间线上，而且没人会发现。

## 分工

与知识库其他 skill 一脉相承：**脚本**做确定性的（快照 / 分类 / 抽文本 / 日期归一 / 渲染 / 校验），
**模型**做语义的（读原文把六要素写出来）。格式由脚本渲染，模型不手写 md——统一格式就是这个 skill 的全部价值。

| 材料 | 谁抽 | 说明 |
|---|---|---|
| txt / md / docx / doc / pdf | 脚本 | 与导入 skill 同一套抽取器（已搬到 `common/kb/extract.py` 共用）；扫描件 PDF、乱码 PDF 拒绝并说明，不做 OCR |
| csv / xlsx | 脚本 | 一行一单；工单号 / 系统 / 时间 / 级别按列名自动填进 `known`，现场 / 判断 / 处置的候选放 `suggest`，仍由模型确认 |
| 照片 / 截图 | **模型** | 脚本点名「需要你看图」，模型用 read 工具打开；HEIC/TIF 多半打不开，如实告诉用户转 jpg/png |
| 其他 | — | 留在清单里标「不支持」，**不算导入** |

## 命令

```bash
S={skills 目录}/gaussdb-kb-init/scripts/kb_init.py
python3 $S scan <文件或目录> [--batch 名]   # 建批次 <kb>/init/<批次>/:sources/ 快照、work/NNN.json 工作单
#   （模型逐个读工作单,把六要素写进 draft/NNN.json;一份材料多个工单就写成数组）
python3 $S render [--batch 名]              # 先验后写:draft → std/*.md + out/<批次>-tickets.md;任一单缺要素整批拒绝并点名
python3 $S validate [--batch 名]            # 复核 std/*.md 还是不是标准格式(手工改过会被拦)
python3 $S status / list                    # 进度 / 批次列表
# 然后交给导入(仍走选择列表闸门):
python3 {skills}/gaussdb-kb/scripts/kb.py ingest <kb>/init/<批次>/out/<批次>-tickets.md --kind tickets
```

退出码与导入 skill 一致：`0` 成功；`1` 运行错误；`2` 有活没干完。

## 验证

- 单测 +55（`test_kb_initstd_units` 40：分类 / 日期 / 渲染逐字稳定 / 校验 / 合并文件；`test_kb_init_skill_units` 15：
  照片被点名、不支持的不丢、表格预填、缺草稿拒绝并点名、有洞的草稿不落盘、非法 JSON、重扫不删草稿）。
- 真材料脚本级端到端：5 份华为问题分析报告 docx + 1 张照片 + 1 张 HEIC + 1 个 zip → scan 抽出 5 份 9–11k 字文本、
  2 张照片点名看图（HEIC 带提示）、zip 留在清单；缺两份草稿时 render 拒绝并点名；补齐后 7 份 std 通过校验；
  `kb.py ingest --kind tickets` 拆成 7 单、`propose` 出 7 份工作单——衔接零改造。
- 容器：只在知识库导入镜像里（runtime 镜像物理没有，冒烟有一条专门验这个）；模型级验收见 gh_agent_k8s
  `scripts/k8s/e2e-kb-init.sh`。

## 已知取舍

- 照片不做 OCR，靠模型视觉。读不清就问用户；这是刻意的——脚本 OCR 出的错字会以「原文」的身份进知识库。
- `kb.py ingest` 处理 md 时把每单命名为 `<批次>-N.md`（现有行为），原始工单号在正文 `- id:` 行里保留。
- 公共安全红线是 19 份 SKILL.md 逐字相同的副本（安全审查要求），其中「只通过本技能脚本取数」一条提到凭据解密，
  对不连库的本 skill 属于泛化措辞；skill 特有的红线在块后单列（只写 `<kb>/init/`、原件只读、不复述 IP/账号）。
