# 初始化白名单：把脚本装进 script_config

`whitelist.md` 里那 98 条脚本怎么进到库里 —— 本地和客户环境是两条不同的路。

> ⚠️ **客户的 GRMP 没有脚本注册接口。**
> 「由于安全原因，目前脚本仅能通过版本 dml 带出」。所以客户环境**没有
> 「调接口初始化」这回事**，只有执行发布 DML。本地 mock 也刻意不挂注册
> 接口 —— 挂上去就等于本地放开了客户不给的权限，到客户环境才发现用不了。

---

## 一、本地（开发/测试）

```bash
export GSDB_HOME=$HOME/.gdaa
export GRMP_AUTH_TOKEN=<任意 32 位十六进制串>

# 从 scripts/registry/ 灌进本地白名单
python3 -m grmp_middleware.grmp_register --db ~/.gdaa/grmp/script_config.db

# 起中间件
python3 -m grmp_middleware.grmp_mock --port 8769
```

只校验不写库：加 `--dry-run`。
重灌（保持原 id 不变）：加 `--replace`。

## 二、客户环境：交付 DML

仓库里已生成两份，**交付用第一份**：

| 文件 | 条数 | 用途 |
|---|---|---|
| [`scripts.sql`](scripts.sql) | **85** | **交付给客户** —— 只含 skill 真正调用的脚本 |
| [`scripts-full.sql`](scripts-full.sql) | 98 | 含中间件自测脚本，仅供本地复现 |

差的 13 条全是中间件自测用的（`perf.*` 9 条是动态性能视图验证场景、
`session.*` 3 条给 demo 脚本、`health.db_info` 给协议测试当样本）——
它们该留在仓库里，**不该混进客户的生产白名单** —— 每条 INSERT 客户都得
走变更评审。

（`vacuum.*` 那 4 条——`dead_tuples` / `autovac_settings` / `autovac_workers` /
`oldest_xmin`——曾经因为 gaussdb-vacuum 这个 skill 还没写而被判定为"未使用"、
排除在外；`vacuum.py` 落地并开始调用它们之后已随之带入 `scripts.sql`，
不再是差集的一部分。）

### 重新生成

```bash
python3 -m grmp_middleware.grmp_register \
    --db /tmp/release.db \
    --dml-out docs/delivery/scripts.sql \
    --exclude-unused \
    --user <真实工号>          # ← 交付前必须改，默认是占位符 grmp-register
```

三个开关的区别：

| 开关 | 行为 |
|---|---|
| （不给） | **拒绝导出**并列出无人调用的脚本，逼你做决定 |
| `--exclude-unused` | 剔掉它们，逐条打印剔了谁 |
| `--include-unused` | 全带上 |

### DML 长什么样

```sql
INSERT INTO grmp.grmp.script_config
  (id, script_type, script_name, database_type, refered_appbusiness,
   kernel_version, region, deployment_form, execute_node_type,
   cluster_deployment_mode, script_content, parameter_config, scene,
   is_valid, create_user, create_time, last_modify_user, last_modify_time,
   is_asyn, "extend", compliance_mode)
VALUES
  ('1', 'SQL', 'explain.plan_text', 'postgres', 1, 'ALL', NULL, NULL, NULL,
   'centralization', 'EXPLAIN (ANALYZE false, BUFFERS false, FORMAT TEXT) {{sql}}
', '[{"key":"sql","value":"","type":"STRING","autoAcquire":false}]',
   'AGENT', 1, 'grmp-register', '2026-08-05 14:59:21.306',
   'grmp-register', NULL, 0, NULL, 'ALL');
```

表名三段式 `grmp.grmp.script_config`（库.模式.表）、列顺序、引号风格、
NULL 写法全按客户样例来 —— 差一点客户就要手工改，手工改就会改错。

## 三、执行前必须确认的三件事

### ① id 冲突 ⚠️

**DML 里的 id 是写死的**（`'1'`、`'2'`…）。如果客户表里已有这些 id，
要么主键冲突导致发布失败（这是好结果，看得见），要么被他们的流程改成覆盖
—— **静默冲掉客户已有的脚本**（这是坏结果）。

执行前先问：

```sql
SELECT COUNT(*), MAX(CAST(id AS INTEGER)) FROM grmp.grmp.script_config;
```

当前工具**还没有 `--id-start` 参数**，起始 id 需要手工调整。

### ② create_user 必须是真实工号

默认值 `grmp-register` 是占位符。用 `--user <工号>` 重新生成。

**注意**：带真实工号的 DML 与 `.db` 不要提交到公开仓库。

### ③ 作用域列全是默认值

7 个作用域列（`region` / `deployment_form` / `execute_node_type` /
`cluster_deployment_mode` / `kernel_version` / `compliance_mode` /
`refered_appbusiness`）我们填的是通用值。客户若靠这些列做可见性过滤，
需要按他们的规则调整 —— 否则脚本可能对目标实例不可见。

## 四、装完怎么验

客户环境没有注册接口，但**接口一可以用来核对装了哪些**：

```bash
curl -s -X POST '<客户地址>/icbc/paas/aiops/grmp/diagnostic/agent/common-operations' \
  -H 'Content-Type: application/json' -H 'auth: <令牌>' \
  -d '{"dataIp":"<目标实例>","offset":1,"limit":1000}' \
  | python3 -c 'import json,sys; r=json.load(sys.stdin)["result"]; \
      print("共", r["total"], "条"); \
      [print(" ", d["id"], d["cmd_name"]) for d in r["list"]]'
```

对照 [`whitelist.md`](whitelist.md) 逐条核，重点看**条数对不对**、
**cmd_name 有没有重复**（重复会让「按名解析 id」变得不确定，
见 [07-调用链路](07-调用链路.md) 最后一节）。

本地同样的核对：

```bash
sqlite3 ~/.gdaa/grmp/script_config.db \
  'SELECT id, script_name FROM script_config ORDER BY CAST(id AS INTEGER)'
```
