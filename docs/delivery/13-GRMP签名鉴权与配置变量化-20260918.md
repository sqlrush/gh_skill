# GRMP 签名鉴权与配置变量化（2026-09-18，skills-v12.12）

对应客户两条新需求（微信截图，`prd/微信图片_20260918142436`、`_20260918150640`）：

1. GRMP API 安全加固——请求头在 `auth` 之外再带 `Appkey`、`Timestamp`、`Signature`。
2. opencode.json 里的 baseURL / model 能否做成变量，测试与生产不用维护两份。

## 1. 签名鉴权

### 1.1 客户已定的

- Appkey 整个智能体一个，名字约定即可；每个 Appkey 对应一对 SM2 公私钥，**密钥对由客户申请后提供给我们**。
- 原文 = 调用 URL 的上下文根 + 时间戳，例 `/v1/validateByNorth/validate+timestamp`；调用方私钥签、GRMP 公钥验。
- 校验目的：调用方范围（Appkey 登记）、重放（Timestamp）、上下文根签名（Signature）。

### 1.2 我们做的（gh_skill `skills-v12.12`，容器仓库 `agent-v0.5`）

- `common/grmp/client.py`：每个请求在 `auth` 之外加三个头，由脚本现算，模型碰不到私钥。四个头的分工：`auth` 认人（按工号），其余三个认应用、防重放、防改路径——**与工号无关，不同用户共用同一个 Appkey 与私钥**。
- `common/grmp/sm3.py`、`sm2.py`：国密 SM3 / SM2 签名的纯 Python 实现（白名单不加包）。正确性三层对照：GB/T 32918 附录固定 k 向量；与 gmssl 互签互验；OpenSSL 3 生成的 PKCS#8 私钥与 DER 签名能解能验。
- `common/grmp/signing.py`：设置解析与签名器。**客户没说清的每一项都可配**，对不上不用改代码：

| 项 | 配置键（`api_connection[].sign`） | 环境变量（优先） | 默认 |
|---|---|---|---|
| 应用名 | `appkey` | `GRMP_APPKEY` | 空 = 不签名（中间件未开校验时照旧） |
| 私钥 | `credential`（凭据名） | `GRMP_SM2_PRIVATE_KEY` | 凭据名 `grmp-sm2`；64 位 hex 或 PEM |
| userId | `user_id` | `GRMP_SIGN_USER_ID` | `1234567812345678`（国标；OpenSSL 默认空串） |
| 时间戳单位 | `timestamp` | `GRMP_SIGN_TIMESTAMP` | `ms` |
| 签名格式 | `format` | `GRMP_SIGN_FORMAT` | `raw`（r‖s 64 字节；Java 默认 `der`） |
| 签名编码 | `encoding` | `GRMP_SIGN_ENCODING` | `hex` |
| 原文模板 | `payload` | `GRMP_SIGN_PAYLOAD` | `{path}+{timestamp}` |

- 配了 Appkey 却拿不到私钥、旋钮值不认识、私钥格式不对：**建连接时就报错**，不会拖到中间件回鉴权失败。
- `grmp_middleware.grmp_mock` 新增同名校验（`--appkey`、`--sm2-public-key`、`--sign-*`），本地对照；`~/kf-verify/kf_signing_e2e.sh` 十项（正向登录 / vacuum / health、负向缺头 / 旋钮不一致 / 缺私钥、场景矩阵 og-grmp 全部经签名 mock）。

### 1.3 非 Pod 部署怎么配

```bash
python3 -m common.credential_cli set grmp-sm2        # 贴客户给的私钥(hex 或 PEM)
```

`config.yaml`：

```yaml
api_connection:
  - host: <中间件>
    port: 80
    token_env: GRMP_AUTH_TOKEN
    appkey: gaussdb-agent            # 与中间件约定的名字
    sign: {credential: grmp-sm2}      # 其余旋钮按 1.4 的确认结果填
```

### 1.4 上线前必须向中间件方确认的（任一项不符 = 全部请求被拒，且与令牌错分不清）

| # | 问题 | 我们的默认 |
|---|---|---|
| 1 | Signature 是 SM2 **签名**（SM3 摘要）还是「公钥加密」？ | 签名 |
| 2 | 签名的 userId | `1234567812345678`；OpenSSL 签出来的默认是空串 |
| 3 | 原文精确拼法：`+` 是否字面；path 是完整路径还是应用根；含不含查询串 | `{path}+{timestamp}`，path = 请求路径 |
| 4 | Timestamp 单位与允许偏差窗口 | 毫秒 |
| 5 | Signature 编码与格式 | hex，raw（Java 默认 DER + base64 的话改两个旋钮） |
| 6 | 私钥文件格式 | hex / PEM 都收 |
| 7 | 生效日期与兼容期 | 未开校验前 `appkey` 留空即可 |
| 8 | 校验失败的响应形态（HTTP 码 / 响应体） | mock 按业务错误模型 |

最省事的对齐方式：请中间件方给一条能通过校验的样例请求（含四个头与原文）或其校验代码片段。

## 2. opencode.json 变量化

opencode 原生支持 `{env:变量名}` 占位符，启动时从环境变量展开（1.18.27 实测：`baseURL`、`apiKey`、`models` 键名、顶层 `model` 四处都展开）。一份文件、两套环境变量：

```jsonc
{
  "share": "disabled",
  "provider": {
    "model-service": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "model-service",
      "options": { "baseURL": "{env:MODEL_BASE_URL}", "apiKey": "{env:MODEL_API_KEY}" },
      "models": { "{env:MODEL_ID}": { "name": "{env:MODEL_ID}" } }
    }
  },
  "model": "model-service/{env:MODEL_ID}"
}
```

**坑**：变量没设时 opencode 不报错，展开成空串（实测 `baseURL = ''`），服务照常起、到调模型才失败。启动脚本先校验：

```bash
for v in MODEL_BASE_URL MODEL_API_KEY MODEL_ID; do [ -n "${!v:-}" ] || { echo "缺少 $v"; exit 1; }; done
```

容器部署不受影响：Pod 启动时按 ConfigMap / Secret 生成配置，缺变量拒绝启动；测试 / 生产是同一镜像 + 两个 kustomize 覆盖层（`k8s/overlays/test`、`prod`）。
