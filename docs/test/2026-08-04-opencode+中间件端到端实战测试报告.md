## 三、场景与结果

### 场景 1：数据库健康检查 ✅

模型自主调用 `gaussdb-health`，采回 12 个维度，产出分级报告。

**采到的真实问题**（都来自库里的实际状态，非模型编造）：

- 缓存命中率 90.5%（阈值 95%）→ 🟠告警
- 慢 SQL 13 条超阈值，其中 `UPDATE ... lock_targets` **avg 15184ms、cpu 仅 0.01s**
  —— 模型正确识别出这是**锁等待型**而非缺索引型，并明确写了「不要盲目建索引」
- 无用索引 10 个，合计约 13.1G
- 统计信息陈旧 4 张表

**一个必须记下来的问题**：bloat 维度采集失败，模型把原因判成了
「中间件白名单拦截了 SQL」，并建议客户「对中间件白名单放行 pg_stat_user_tables
相关只读查询后复检」。

**这个归因是错的。** 真实原因是 `health.bloat` 那条 SQL 自己有个悬空的 `+`
（`WHERE t.n_dead_tup > 0+`，见既有缺陷清单第 7 条，你此前指示只报不修）。
中间件什么都没拦，是 SQL 语法错误。

按这个建议做，客户会去找中间件团队白跑一趟。**降级消息说清「哪一层失败」很重要**
——错误里带着 `SQLSTATE 42601`，但模型仍然归因到了中间件。详见第五节。

---

### 场景 2：慢 SQL 定位与调优 ✅（并暴露 2 个缺陷）

模型的处置链路完全正确：`slowsql` 定位 → `sqlfetch` 取原文 → 尝试 `sqltune` 深调。

**中间件模式的能力边界被正确拒绝**：

```
error: 连接 og-grmp 的 driver 是 grmp：中间件的执行接口每次调用都是独立连接，
不提供跨语句的持久会话。
```

模型没有绕过去，也没有编造调优结论，而是如实转述：

> sqltune 的两项核心能力都要求一条原始数据库会话……
> **该能力在白名单模型下不可用。**
> ……缺了执行计划的证据包不足以支撑调优结论，所以整条命令在此停止，不做半份输出。

这正是设计意图——**宁可拒绝，不给半份结论**。

**本场景抓到的两个缺陷见第四节。**

---

### 场景 3：WDR 解读 ✅

模型取了快照窗口（193 分钟）的负载画像、等待事件、TOP SQL、缓存与检查点，
给出了有判断力的解读：

- 识别出 TOP SQL 占 DB time 64.89% 的那条是**监控轮询**（`gs_session_memory_detail`
  每 20 秒一次，569 次），不是业务 SQL；并指出它是内存型系统视图、无法建索引、
  执行计划层面没有可优化项，建议降低轮询频率而不是"优化 SQL"
- 对「IO_EVENT 占等待 100%」没有当成瓶颈，而是指出**绝对量只有 12s / 193min**，
  且物理读 Top 对象全是 WDR 快照自己的历史表，cache_hit 99.99%，
  结论是「业务侧无需处理」

这一段的判断质量值得单独说：**它抵抗住了「占比高就是瓶颈」这个最常见的误读。**

---

### 场景 4：慢 SQL 复测（验证修复）✅

修复后重跑，让模型「把表名原样抄出来供核对」。全部正确：

| 修复前（报告里显示的） | 修复后（正确的） |
|---|---|
| `dbe_perf. tatement_hi tory` | `dbe_perf.statement_history` |
| `g bench_e2e_20260801_100g` | `gsbench_e2e_20260801_100g` |
| `( tat _corr_a, tat _corr_b)` | `(stats_corr_a,stats_corr_b)` |
| **`lock_target`** | **`lock_targets`** |

最后一行最能说明危害：修复前表名少了结尾的 `s`，**`lock_target` 这张表根本不存在**。
DBA 照着报告去查，只会得到 "relation does not exist"，然后怀疑是自己权限不对。

模型还主动指出了 schema 引用风格不一致（有的带引号有的不带），并声明「这是应用端
两种写法混用，不是我抄错」——这种自我区分很有用。

### 场景 5：内存分析 + TOP SQL + 对象审查 ✅

三个 skill 串起来跑：

- **memanalyze**：当前内存 76.1%、峰值曾达 99.5%，定位到主因是 AutoVacWorker
  清理 `statement_history` 撑起 TopTransactionContext 1GB。**模型明确标注 L4 层
  未采到 SQL 级数据，因此"无法把 Top SQL 与内存峰值直接关联"** —— 没有强行关联
- **topsql**：TOP 5 按总耗时排，识别出 #3 是「511 万次调用 × 0.9ms」的小查询高调用型
- **sqlreview**：`public` 有 2 张表无主键（error）；`gsbench` schema 16 个索引
  命名违规（warn）+ 一批 `scans=0` 的疑似冗余索引

### 场景 6：实时阻塞链 + 存储过程分析 ✅

- **阻塞链**：采集瞬间没有活跃阻塞。模型没有硬凑结论，而是写「上一轮争用已释放，
  或在两次采集之间」，并建议在争用发生那一刻重跑

## 四、本轮抓到的缺陷（均已修复）

### 缺陷 A：慢 SQL 报告里的表名被悄悄改掉 🔴

**现象**：所有展示 SQL 正文的报告里，字母 `s` 全部变成了空格。

**根因**：

```sql
LEFT(REGEXP_REPLACE(query, E'\s+', ' ', 'g'), 180) AS query
```

openGauss/PostgreSQL 的 `E''` 是**转义字符串**：反斜杠后跟未定义的转义字符时，
反斜杠被丢掉、字符按字面留下。于是 `E'\s+'` 到正则引擎手里是 `'s+'`
—— 匹配字母 s，不是空白。「压缩连续空白」变成了「把连续的 s 换成空格」。

库上实测：

```
E'\s+'  ->  ' elect   tat  from  dbe_perf. tatement_hi tory'
'\s+'   ->  'select stats from dbe_perf.statement_history'
```

**影响**：4 条脚本，全是给 DBA 看 SQL 正文的那几条 ——
`slowsql.slow_sql`、`health.slow_sql`、`perf.sessions`、`topsql.top_sql`。

**为什么之前所有测试都没抓到**：

1. 它**不报错**，只是把内容改了
2. 双路径一致性检查也抓不到 —— 它比的是「同一条 SQL 走两条链路」，
   两条链路跑的是同一条坏 SQL，一起错，输出照样逐字节一致
3. 单测用的是构造数据，构造数据里的表名不一定含 `s`

**修复**：去掉 `E` 前缀。补了静态检查扫全部 81 条脚本，
`E''` 里出现 `\s\w\d\b` 之类正则字符类就红。

---

### 缺陷 B：慢 SQL 一多，整条命令就崩 🟠

**现象**：

```
error: [Errno 2] No such file or directory:
       '/Users/sqlrush/.config/opencode/csv/slow_sql_export_20260804_220430.csv'
```

**根因**：客户在 `slowsql.py` 里加的「新增逻辑」——超过 10 条时写 CSV，
但**不建目录**。而且它恰恰在「库里慢 SQL 多」时才触发，也就是最需要这条命令的时候。

**这个错误的坏处在于它看起来像取数失败**，不像导出失败。模型是读了源码才搞清楚
的（它自己 mkdir 之后重跑成功，处置正确，但真实客户现场不会有人去读源码）。

**顺带发现**：同一段里 `--export` 用的是 `type=bool`，那就是 `bool(str)`：
非空字符串一律为真，于是 `--export false` 反而打开了导出。与 `bool("f")` 是
同一个坑，换了个地方。

**修复**：导出目录自己建；`--export` 改成 `store_true`。

## 五、需要你决定的一件事

**`health.bloat` 的降级消息会把人引到错误的方向。**

那条 SQL 有悬空的 `+`（既有缺陷第 7 条），你此前指示只报不修。本轮实测的后果是：
模型把 `SQLSTATE 42601` 归因成「中间件白名单拦截」，并建议客户去改中间件配置。

这不是模型的问题——降级消息里只说了「采集失败」，没说清失败在哪一层。
在客户现场，这会变成一次白跑的跨团队沟通。

三个选择：

1. **修那条 SQL**（一个字符），bloat 维度恢复可用
2. **不修，但把降级消息写清楚**：注明「本条脚本已知存在语法缺陷，与访问通道无关，
   不要去查中间件配置」
3. **维持现状**

我倾向 1 —— 它就是个手误，修了还能多一个维度。但你之前说不修，所以我没动。

  静默少一项。见既有缺陷清单第 10 条，仍待你决定

  这是被测库里的现象，不是 skill 的问题，但模型主动指出来了，是好事
