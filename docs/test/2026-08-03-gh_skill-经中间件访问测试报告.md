# gh_skill 经 GRMP 中间件访问数据库 —— 测试报告

**日期**：2026-08-03
**被测**：`common/sql.py` 的全部 49 条 SQL 模板，经 grmp-mock（HTTP）访问 og5
**方式**：批量转成 GRMP 脚本 → 注册 → 经**真实 HTTP 接口**逐条执行 → 对照直连路径
**探针脚本**：`~/gh_skill/.probe/`（仓库外，未入库）

---

## 一、结论

| 指标 | 结果 |
|---|---|
| 注册通过 | **49 / 49** |
| 经中间件执行通过 | **47 / 49** |
| 失败 2 条 | **都是 gh_skill 自身的既有缺陷，直连路径同样失败**，与中间件无关 |
| 迁移需人工改动 | **6 条**（补引号） |
| 触发风险标注 | 20 条（STRING_PARAM 16、IDENT_POSITION 7、MULTI_VALUE 1、NON_READONLY 1） |

**主结论：gh_skill 现有的固定模板类 SQL，绝大部分可以走 GRMP 白名单模式。**
真正的障碍不在数量，在下面五个发现里。

## 二、发现 1：两条模板本身就是坏的（与中间件无关）

### `skill_health_008` —— Python 源码被粘进了字符串

`common/sql.py:97-100`：

```python
skill_health_008 = """
("SELECT COALESCE(state,'<null>') AS state, count(*) "
           "FROM pg_stat_activity GROUP BY state ORDER BY 2 DESC")
           """
```

写的时候把 Python 的隐式字符串拼接**连同括号和引号**一起粘进了三引号里。
实际执行的是以 `("SELECT …` 开头的文本。

```
ERROR: syntax error at or near ""SELECT COALESCE(state,'<null>') AS state, count(*) ""
```

**直连路径同样失败**，且 `skills/gaussdb-health/scripts/collectors.py:341` 正在用它
（`_CONN_Q = skill_health_008`）——health skill 的连接状态统计目前是坏的。

### `skill_health_005` —— 悬空的加号

```sql
WHERE t.n_dead_tup > 0+
  AND t.schemaname NOT IN (...)
```

`0+` 后面没有操作数。推测原本是 `> 0+%s` 之类，`%s` 丢了（该模板末尾另有一个
`LIMIT %s`）。

```
ERROR: syntax error at or near "AND"
```

**直连路径同样失败。**

> 这两条是本次测试的**意外收获**：它们与中间件无关，是把全部 SQL 拿去真跑一遍
> 才暴露出来的。建议单独修，不要混进迁移工作。

## 三、发现 2：13 条模板用绑定变量，其中 6 条迁移时必须手工补引号

`common/sql.py` 里有两套参数机制并存：

| 机制 | 数量 | 迁移方式 |
|---|---|---|
| f-string `{x}` | 多数 | 直接换成 `{{x}}` |
| 绑定变量 `%s` | **13 条** | 换成 `{{pN}}`，**字符串位要补引号** |

`%s` 的 13 条按取值类型再分：

| 类型 | 模板 | 迁移 |
|---|---|---|
| 数值（阈值 / LIMIT） | health_003/004/005/006/007/011/012 | 直接换，无需改动 |
| **字符串**（表名 / schema 名） | **memanalyze_001/002、procinfo_001、proctune_005、sqlreview_001/002** | **必须补引号** |

原因：绑定变量下驱动会替字符串加引号，所以模板里写的是

```sql
WHERE p.proname = %s AND (%s = '' OR n.nspname = %s)
```

换成文本替换后变成 `WHERE p.proname = {{p1}}`，渲染出

```sql
WHERE p.proname = pg_sleep        -- 被当成列名
ERROR: invalid input syntax for integer: ""   /   column "pg_sleep" does not exist
```

补上引号（`= '{{p1}}'`）后 6 条全部通过。

### 这条风险的严重性要分开看

- **多数情况下会报错**（列不存在 / 类型错误）→ 吵闹地失败，能发现
- **但存在静默出错的路径**：若某个字符串参数的取值恰好是纯数字，
  `WHERE id = {{p1}}` 渲染成 `WHERE id = 123` 语法合法、语义可能不同
- **更要紧的是**：绑定变量本来把注入挡住了，改成文本替换后这道防线消失
  （见发现 3）

**迁移时这 13 条必须逐条人工过一遍，不能机械替换。**

## 四、发现 3：16 条模板迁移后带有可利用的注入面

风险标注分布（49 条中）：

| 标注 | 条数 | 含义 |
|---|---|---|
| `STRING_PARAM` | **16** | 有 String 参数。五种类型里只有它没有格式约束 |
| `IDENT_POSITION` | 7 | 占位符落在表名/列名/ORDER BY 位 |
| `MULTI_VALUE` | 1 | 占位符在 `IN (...)` 内 |
| `NON_READONLY` | 1 | 非只读语句（即 health_008，因它以 `(` 开头被判为非 SELECT） |
| 无标注 | 29 | |

实测（`session.by_user`，`where usename = '{{username}}'`）：

```
正常（传不存在的用户名）: rows = 0
传 no_such_user_zz9' or '1'='1 : rows = 18      ← 返回全表
```

**这不是中间件缺陷，是文本替换的固有结果。** 客户中间件若也用 `String.replace`
实现，客户环境存在同一个洞。

值得注意的是 `{names}` / `{schemas}` / `{schema_filter}` 这类参数——
它们在原模板里是**整段 SQL 片段**（如 `('a','b')`），GRMP 没有列表类型，
只能当 String 整体塞进去。这类参数的注入面比普通值参数更大。

**建议向客户确认：GRMP 对 String 参数是否做转义或绑定。**
若不做，其现有脚本库里所有带 String 参数的脚本都有同样问题。

## 五、发现 4：任意 SQL 能通过「直通脚本」进入，白名单被穿透

注册一条：

```yaml
name: explain.passthrough
sql: EXPLAIN {{user_sql}};
params: [{key: user_sql, type: String}]
```

实测**全部跑通**：

```
EXPLAIN select 1                              → OK
EXPLAIN select * from pg_class where ...      → OK
EXPLAIN select 1; -- 任意语句都能从这条进来      → OK
```

**技术上 explain / sqlreview 这类需要任意 SQL 的 skill 可以这样迁移。**
但这等于在白名单上开了一个通用入口——任何 SQL 都能从这条脚本进去，
白名单的意义被架空。

**这是客户的安全策略问题，不是技术问题。** 三个选项：

1. 接受直通脚本（白名单形同虚设）
2. 为任意 SQL 类诊断保留一条直连通道（我倾向这个，它同时解决发现 5）
3. 客户环境不提供这类 skill

## 六、发现 5：会话状态不跨调用留存 —— 实测确认

接口二每次调用建立独立连接，执行完即关闭。实测：

```
同一条连接内：  set work_mem='63MB'  →  show work_mem = 63MB
经中间件两次调用：第 1 次 set，第 2 次 show  →  show work_mem = 16MB（默认值）
```

**影响的是 hypopg 虚拟索引验证**：`hypopg_create_index()` 建的虚拟索引是会话级的，
下一次调用就没了，`EXPLAIN` 看到的仍是原计划——**执行成功、结论错误、不报错**。

涉及 `skills/gaussdb-sqltune/hypoindex.py` 与 `skills/gaussdb-proctune/hypoindex.py`。

> og5（openGauss-lite 5.0.3）**未安装 hypopg**，所以无法直接演示虚拟索引失效，
> 改用会话级 GUC 证明了同一件事：会话状态不留存。

### 这里有一个必须补的守卫

仓库**已经有**这个问题的防线：`tests/test_hypopg_session_guard.py` 说明
gsql 后端因为每条语句起独立子进程，同样不提供持久会话，所以
`verify_indexes` 入口会明确报错而不是静默失效。

**中间件路径缺同款守卫。** `common/access.py` 返回的 runner 没有
`provides_session` 概念，一旦 P6 把 sqltune/proctune 迁到 `access`，
hypopg 验证会**静默失效**——正是仓库当初为 gsql 加守卫要防的那件事。

**这是迁移 sqltune/proctune 之前必须先补的。**

## 八、本次测试没能覆盖的

| 项 | 原因 |
|---|---|
| hypopg 虚拟索引真实失效场景 | og5 未安装 hypopg，用 GUC 间接证明 |

| 分布式部署下的行为 | 只有单实例 og5 |
| GaussDB（非 lite）的系统视图差异 | 手上只有 openGauss-lite 5.0.3 |
| 大结果集与超时 | 未构造超过 10000 行 / 60 秒的用例 |
| 并发调用 | 未测 |

**注意**：本报告全部结论基于 og5。客户是 GaussDB，同一条 SQL 的系统视图字段集、
执行计划、报错文本都可能不同。**「本地 47/49 通过」推不出「客户 47/49 通过」。**
