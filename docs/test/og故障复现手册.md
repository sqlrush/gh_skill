# og 故障复现手册（faultlab）

在 openGauss 测试库上**一条命令造出 34 项典型性能问题、持续 20 分钟，再一条命令清干净**，
可以反复跑。用来检验这套 `gaussdb-*` 诊断 skill：面对已知的故障，它们报不报、报得对不对。

工具在 `tools/faultlab/`，预期发现矩阵在 `tools/faultlab/expected.yaml`。

> **只在测试库上跑。** 它会关掉表级 autovacuum、建复制槽、留孤儿两阶段事务、做 VACUUM FULL。
> 启动前会核对实例指纹，对不上就拒绝执行；但请不要去改那道核对。

## 1. 前置条件

| 要求 | 说明 |
|---|---|
| 目标库 | openGauss 测试实例。默认按 og5 配好：容器名 `og5`，Mac 上 `127.0.0.1:5433`，库 `postgres` |
| 解释器 | 要装了 `psycopg2`。Mac 上用 `~/p2venv/bin/python` |
| 容器可执行 | 建专用用户与打 WDR 快照要 `omm` 权限，经 `docker exec` 完成，所以要能跑 `docker` |
| 磁盘 | 数据约 900 MB；跑的过程中临时文件与 WAL 另算，留 5 GB 余量 |
| 宿主机文件表 | 落盘类场景（S2/S6）会产生大量临时文件。**macOS 上先确认文件表有余量**：`sysctl vfs.vnstats.num_free_vnodes kern.num_files kern.maxfiles`，空闲 vnode 不到 10 万、或打开文件数超过上限的 3/4 时不要开跑（见 §6「跑到一半 og5 自己重启了」）。**不要看 `kern.num_vnodes` 是否等于 `kern.maxvnodes`**：那是已分配数，macOS 分配满之后不归还，机器开久了一直相等 |

换别的实例：在 `~/.faultlab/conn.json` 里写覆盖值（只写要改的字段）。

```json
{ "host": "127.0.0.1", "port": 5433, "dbname": "postgres", "container": "og5" }
```

## 2. 快速开始

```bash
cd ~/gh_skill/opencode_skill-main-v2-0729
P=~/p2venv/bin/python

$P tools/faultlab/faultlab.py check       # 环境自检，只读，不改任何东西
$P tools/faultlab/faultlab.py prepare     # 建用户 + 造数据，约 15 秒，**一次就够**
$P tools/faultlab/faultlab.py calibrate   # 校准慢 SQL 规模，约 20 秒，**换机器后跑一次**
$P tools/faultlab/faultlab.py run         # 造故障：1 分钟基线 + 20 分钟故障 + 清理 + 1 分钟恢复
```

跑的过程中**另开一个终端**看现象：

```bash
$P tools/faultlab/faultlab.py status --watch 10
```

跑完之后出报告（各场景的起止时刻、快照号，拿去对 WDR 窗口和 skill 输出）：

```bash
$P tools/faultlab/faultlab.py report
$P tools/faultlab/faultlab.py expected    # 预期发现矩阵：格式核对 + actual 还剩几项没填（见 §7）
```

**建议用 `nohup` 跑 `run`**，这样终端断了也不影响（故障会按窗口自己结束）：

```bash
(nohup $P tools/faultlab/faultlab.py run > /tmp/faultlab.log 2>&1 &)
tail -f /tmp/faultlab.log
```

### 只跑一类 / 只跑几项

```bash
$P tools/faultlab/faultlab.py run --only lock,deadlock --window 600
$P tools/faultlab/faultlab.py run --codes K5,V6 --window 180 --quiet 0
```

分类：`slow`（慢 SQL）、`lock`（锁等待）、`deadlock`（死锁）、`vacuum`、`lwlock`（轻量锁）。
**全部一起跑** 时各类现象会互相影响（库整体变卡），这是故意的——现场就是这样。
要拿干净信号做单项验证时用 `--only`。

`--codes` 按编号挑，并把挑出来的几项**整体前移**到窗口第 5 秒起跑（时长与先后不变）——
在共用的 og5 上验证某一项能不能造出来时，不用为了等排在 +910 秒的 V6 陪跑十几分钟。
`--only` 与 `--codes` 二选一。窗口要比挑出来那几项的时段长，否则会被窗口截断。

> **第一次跑新版本时多两分钟：** `run` 在基线之前会补建运行期对象（K5/V6 用的慢表达式函数、
> V6 的 `maint_hist`、L3 的 `xact_tick`、L5 的 `subx_log`，以及把 L2 的 `hotpage` 换成 ustore 表）。
> 已经有的不动；`maint_hist` 那条慢表达式索引第一次要建约两分钟。`check` 会提示这几样还没建，
> 那不是「数据没备好」，不用重跑 `prepare`。

## 3. 34 项场景

### 3.1 慢 SQL（S1–S7）

每条 5~7 张表、多层嵌套。SQL 原文在 `tools/faultlab/sql/slow/*.sql`，每个文件开头写明了成因。

| 编号 | 造的是什么 | 怎么慢的 | 窗口内 |
|---|---|---|---|
| S1 | 相关子查询逐行执行 | `payments.order_id` 没索引，每取一行订单扫两遍百万行表 | **跑不完**（设计如此） |
| S2 | 三层派生表 + `LIKE` 前缀关联 | 前缀来自另一张表的列，索引用不上，20 万 × 20 万嵌套循环；外加 4MB work_mem 下哈希聚合落盘 | **跑不完** |
| S3 | `NOT IN` 碰上可空列 | 不能改写成反连接，退化成逐行子计划 | 约 8 分钟跑完 |
| S4 | 索引列上套类型转换 | `c.code::bigint = o.cust_id`，`idx_customers_code` 失效 | 约 3 分钟跑完 |
| S5 | 统计信息过期 + 数据倾斜 | 估几行、实际上万行（`cust_id=1` 占三分之一），选了嵌套循环 | 约 8 分钟跑完 |
| S6 | 四个窗口函数 + 2MB work_mem | 每次排序都落盘（external merge，落几百 MB） | 约 30 秒一次，循环 |

> **S2 以前不是「跑不完」：** 第一版按编码前 8 位归集，只分出约 2000 组，1~2 分钟就跑完一次
> （2026-10-24 那轮跑完了 13 次），和这张表、`expected.yaml` 写的「一直 active」对不上。
> 现在按完整编码归集（20 万组），窗口里铁定跑不完。
>
> **S5 依赖 V7 的统计信息一直是过期的。** 2026-10-24 那轮 `import_stage` 导入 80 秒后就被自动
> ANALYZE 了，估算变准，S5 就不成立了（见 §3.4 V7）。看 S5 之前先看 V7 的自证。
>
> **会跑完的几条（S3–S6）按排期停时，不打断正在跑的那一轮**，让它跑完再进执行历史；
> 窗口结束时才一律停掉。所以忙的时候 S3 的最后一轮可能拖过它自己的时段。
> 慢 SQL 停的时候**终止会话、不取消语句**：openGauss 会把被取消的语句也记进 `dbe_perf.statement`
> （2026-10-24 第二轮 S1 被取消后，执行历史里多了一条「1 次、1182 秒、CPU 0」，S2、S5 也一样），
> 一直跑不完的 S1/S2 就不再是「历史里没有」，topsql 的平均耗时榜也被它们占了。终止会话则不记。
| S7 | 高频点查 | `cust_code` 没索引，每次全表扫；单次零点几秒，靠**次数**堆出总耗时 | 一直跑 |

**S1/S2 与 S3–S6 的分工，是这一类的关键：**

- **S1/S2 一直跑不完** → 造的是「现在有一条 SQL 已经跑了十几分钟」。
  看它的是 health / lockwait / waitevent——它们读 `pg_stat_activity`，只看得到**正在执行**的。
- **S3–S6 会跑完** → 造的是「执行历史里有几分钟的 SQL」。
  看它的是 topsql / slowsql / wdr——它们读 `dbe_perf` 的统计，**只统计已完成的执行**，
  一直没跑完的 S1/S2 在那里一行都没有。
- **S7 高频** → 让「总耗时榜首」和「单条最慢」不是同一条。这两张榜本来就不该相同。

### 3.2 锁等待（K1–K10）

覆盖 `transactionid`、`tuple`、`relation`、`extend`、`advisory` 五种锁类型，以及「持锁者根本不在会话里」。

| 编号 | 造的是什么 | 现场的样子 |
|---|---|---|
| K1 | **四层**行锁阻塞链，根会话改完行后空闲不提交 | 杀链条中间那个解不开，必须杀最根上那个 |
| K10 | 孤儿两阶段事务：`PREPARE` 后会话退出 | **杀会话也解不开**——持锁者不在 `pg_stat_activity` 里 |
| K4 | 月结任务 `LOCK TABLE IN EXCLUSIVE MODE`，锁 2 分钟放 1 分钟 | 「每小时总有几分钟特别卡」，赶到时已经放开了 |
| K6 | 外键父子表互等 | 主数据维护与业务写入同时跑，两边都不觉得自己在加锁 |
| K7 | 多会话插同一个主键 | 等的是 `transactionid`，`pg_locks` 里看不到行锁 |
| K8 | 咨询锁（advisory）排队 | 没有任何表被锁，业务就是过不去 |
| K2 | 批处理 `FOR UPDATE` 分批锁行（只用 `acct` 1001~2000 号行） | **抖动型**：瞬时查询常常什么都看不到，要看一段时间的统计 |
| K5 | 不带 `CONCURRENTLY` 建索引（慢表达式索引，整个时段都在建） | 白天「顺手加个索引」，这张表的写入全部超时 |
| K3 | **DDL 锁队列放大** | 一个只读长查询 + 一个加字段，把整张表的读写全冻住 |
| K9 | 并发插入抢表扩展锁 | 批量导入「越加并发越不快」 |

K3 最反直觉，也最值得用来检验工具：长查询本来谁也不挡，但 `ALTER TABLE` 要等它，
而 ALTER 已经在队列里排上了表级排他锁，**后面所有读写都得排在 ALTER 之后**。
根因是那个长查询，不是 ALTER——报错了对象，运维就会去杀错的会话。

**K3 停下时会取消那条还在排队的 ALTER。** 2026-10-24 那轮它按排期停下，ALTER 却一直挂在
`fl.payments` 上（停止位叫不醒一条正在等锁的 SQL），后面的 S5、`status`、explain、health
全被堵住，最后是人工取消的。现在停场景分三步：置停止位 → 还在跑的取消当前语句 → 还在的终止会话
（只按 `application_name` 认 `fl:` 自己的会话），而且每条会话的等锁上限按它自己的时段算（见 §5）。

**K2 与 K5 的两处改动（2026-10-24 那轮没按设计造出来）：**

- K2 原来从 1 号行扫起，在线更新也满表跳，一上来就撞上 K1 根会话锁着的 1~3 号行，
  批处理在 1 号行上一等就是 18 分钟——抖动型变成了持续阻塞。现在只用 1001~2000 号行，
  别的场景用到的行都在 200 号以内。
- K5 原来循环「建普通索引（7 秒）→ 等 20 秒 → 删」，写入被挡的时间不到三成；更糟的是
  `DROP INDEX` 要整表排他锁、排在 S2/S3 的长查询后面，写入又排在 DROP 后面——看起来像 K3。
  现在建的是慢表达式索引（每行算一次 `fl_slow_key`），时段内只建一次、不删，整个时段写入都被挡；
  时段一到停场景时把它取消，不留索引。万一机器快提前建完，索引留到 `cleanup` 再删。

### 3.3 死锁（D1–D6）

一个驱动会话轮流演六种形态，约 30 秒一次，20 分钟大约 35 次。

| 编号 | 形态 | 该给的建议 |
|---|---|---|
| D1 | 两会话交叉更新同表两行 | 统一加锁顺序 |
| D2 | 三会话成环 | 同上，但要能看出是环 |
| D3 | 跨表加锁顺序相反 | 统一表的访问顺序 |
| D4 | 锁升级：都先 `FOR SHARE` 再都 `UPDATE` | 一开始就 `FOR UPDATE` |
| D5 | 外键引起 | 调整父子表写入顺序 |
| D6 | 唯一索引按相反顺序插入 | 按序插入 / 批量前排序 |

D4 最隐蔽：两笔事务一开始「只是读」，代码里看不到任何交叉加锁的痕迹。

**D3 / D5 用自己的外键子表 `dl_child`**（运行期对象，100 行，外键指向 `acct`）。原来它们用 `acct_child`，
而 K4 每 3 分钟有 2 分钟用 `LOCK TABLE` 锁着它：2026-10-24 第二轮 D5 三轮都卡在那把表锁上（死锁 +0），
D3 也只撞出 2 次。

> **死锁牺牲者收到的报错是预期的**，不算运行失败。运行结束时统计的「出错的会话」
> 已经把这类预期报错排除了。

### 3.4 VACUUM（V1–V7）

这一类有一条贯穿的主线：**死元组清不掉的原因不止一个，而解法完全不同。**
诊断工具的价值就在于分清是哪一种——报一句「有死元组」等于没说。

| 编号 | 原因 | 解法 |
|---|---|---|
| V1 | autovacuum 被**关掉**了 | 开回去 |
| V5 | autovacuum **开着**，但被限速到追不上 | 调 `cost_delay` / `cost_limit` |
| V2 | 长事务持着旧快照 | 去找那笔事务；改 autovacuum 没用 |
| V3 | 两阶段事务 | `ROLLBACK PREPARED`——连会话都没有 |
| V4 | 复制槽（逻辑槽）没人消费 | 删槽或让消费端跟上 |
| V6 | 业务高峰做 `VACUUM FULL`（对象 `maint_hist`，整个时段反复做） | 空间收回来了，代价是这张表读写全断 |
| V7 | 导入后不收集统计信息 | `ANALYZE`（它也是 S5 的成因） |

V1 与 V5 的区别最该被工具分清：V5 里 `last_autovacuum` 一直在更新，
**只看「autovacuum 开没开」会判成正常**。

**2026-10-24 那轮之后改的四项：**

- **V4 改成逻辑复制槽。** 原来的物理槽没有备机连上来，`restart_lsn`、`xmin` 一直是空的——
  既不留 WAL 也不钉水位，等于什么都没造。逻辑槽（插件 `mppdb_decoding`，og5 的 `wal_level=logical`）
  一建好就有 `restart_lsn` 与 `catalog_xmin`。建逻辑槽要等当时所有已分配事务号的事务结束，
  所以 V4 排在最前（+2 秒，抢在 K1/K10/V2/V3 之前），建槽限 30 秒；建不成退回「物理槽 + 推进到当前位置」，
  再不成自证会写「没造出来」。WAL 守卫照旧：槽建立以来 WAL 涨过 2 GB 就删槽。
  **逻辑槽会让 WAL 持续堆积，全量一轮约 10 GB**（2026-10-24 第二轮：restart_lsn 之后积了 10223 MB，
  pg_xlog 到 11 GB；守卫看的是 WAL 目录的增量，og5 平时就留着好几 GB，所以没触发），
  跑完 cleanup 删槽后等 checkpoint 回收。开跑前确认盘上留够余量。
  **别人的长写事务也会挡住它：** 2026-10-24 分组验证时 og5 上正好有一笔别的测试留下的
  `idle in transaction`（不是 `fl:` 的会话，本工具不碰），逻辑槽 30 秒没建成，退回了物理槽——
  那样能钉住 WAL（`restart_lsn` 有值、WAL 开始涨），但 `xmin` / `catalog_xmin` 仍是空的，
  vacuum 的 R4 看不到这个来源。全量跑前确认 og5 上没有别人的长写事务；V4 的自证写的是
  「physical」还是「logical」，填 `actual` 时照实写。
- **V5 的限速放宽到默认速度的三成**（`cost_delay=20ms` / `cost_limit=60`）。原来 100ms / 10 太狠，
  一轮都跑不完——`last_autovacuum` 只在一轮**结束**时更新，于是一直是空的，看起来和 V1 关掉了一样。
  现在一轮几十秒，时段内跑好几轮；自证写「跑了 N 轮还追不上」。死元组照样清不掉，因为回收水位被
  V2/V3/K10 卡着——这也是现场「限速 + 长事务」叠在一起的样子，工具应同时报 R3 与 R4、不报 R2。
- **V6 换了对象、反复做。** 原来对 `bloat_hot` 做一次 VACUUM FULL，10 秒就完，排查的人基本赶不上；
  想让它变长只能让表更大，而 `bloat_hot` 重写一次就是 500 多 MB 的 WAL（V4 的槽正钉着 WAL）。
  现在对象是 unlogged 表 `maint_hist`（重写不产生 WAL），带一条慢表达式索引，每次重建约两分钟，
  整个时段反复做，时段一到把正在做的那次取消。不再做 `bloat_hot` 的前后对比——回收水位被卡着，
  VACUUM FULL 也收不回那些死元组（那轮做完反而更大）。
- **V7 加了表级 analyze 触发线。** og5 上实测，`autovacuum_enabled = false` **挡不住**自动 ANALYZE：
  那轮 `import_stage` 导入 80 秒后就有了统计信息（`last_autoanalyze` 有值），`bloat_hot` 在关着
  autovacuum 的 20 分钟里被自动分析了 101 次。现在再加两条**表级**参数
  （`autovacuum_analyze_threshold = 2000000000`、`autovacuum_analyze_scale_factor = 100`），
  触发线永远够不着；实例级参数一个不动。V7 排到窗口结束、每分钟自证一次，
  一旦写出「已被自动 ANALYZE」，S5 就不成立，填 `actual` 时要如实写。
  **V7 每次导入前重建这张表**（不是 TRUNCATE）：TRUNCATE 清不掉 `pg_statistic` 里的列统计。2026-10-24 第二轮，
  上午那次自动 ANALYZE 留下的 `cust_id` 高频值一直在，导入的又是同分布的数据，S5 估 11304 行、实际约 11026 行，
  估得很准，根本没有「统计过期」。运行期补建的几张表建完就 ANALYZE，不再当成「从没分析过」出现在 STALE_STATS 里。

### 3.5 轻量锁（L1–L5）

| 编号 | 造的是什么 | 预期等待事件 | 时间段 |
|---|---|---|---|
| L1 | 提交风暴：单行插入 + 每条即提交 | `WALInsertLock` / `WALWriteLock` / `WALFlushWait` | 0~4 分钟 |
| L2 | 热点页：3 会话异步提交、各改同一页上的不同行（ustore 原地更新） | `BufferContentLock` | 4~8 分钟 |
| L3 | 极短**写**事务高频提交（异步提交；能在匿名块里循环 COMMIT 就在服务端循环） | `XidGenLock` / `ProcArrayLock` / CSN 相关 | 8~12 分钟 |
| L4 | 千分区表：每条语句锁 200 个分区、语句级提交 | `LockMgrLock` | 12~16 分钟 |
| L5 | 2 会话每事务数百个**写**子事务（`EXCEPTION` 块）+ 1 会话并发读 | `SubtransControlLock` / CLog 相关 | 16~20 分钟 |

**L2–L5 在 2026-10-24 那轮几乎都没争起来，各有原因，分别改了：**

- L2：每条更新即提交、同步刷盘，时间全花在等 WAL 刷盘（自证里全是 `WALFlushWait`）；
  而且回收水位被 V2/V3/K10 卡着，普通表每次更新留一个清不掉的旧版本，100 行很快散到几百个页上，
  「热点页」不复存在。现在会话级 `synchronous_commit=off`，`hotpage` 换成 ustore 表（原地更新，页不胀开）。
- L3：原来是只读小事务——只读事务不分配事务号；BEGIN / SELECT / COMMIT 三次往返，时间耗在客户端往返上
  （自证里全是 `wait cmd`，还被误算成「在等」）。现在是写事务 + 异步提交，各改 `xact_tick` 里自己那一行。
- L4：同样被往返拖住了锁申请频率，而且 `count(*)` 要扫完 200 个分区的 2 万行，CPU 占满。
  现在在匿名块里循环「`LIMIT 1` 拿 200 个分区锁 → COMMIT」：锁在执行器启动时就全拿了，扫到第一行就收手。
- L5：原来子事务里只做 SELECT——不分配子事务号，根本不进子事务映射；也没有并发读的会话。
  现在每个子事务插一行 `subx_log`（写的两条异步提交），第三条会话一直读这张表。

块内 COMMIT（`DO $$ … COMMIT; … $$`）是开跑时探测出来的：内核不支持就退回「一条语句一个事务」，
L3 的时间线里会写明用的是哪一种（og5 支持）。ustore 不可用的实例上 `hotpage` / `xact_tick` 退回普通表，
补建时会写明——那时 L2 多半还是争不起来。

**og5 上分组单跑的实测（2026-10-24，每段一个快照窗口，用 gaussdb-waitevent 看）：**

| 段 | LWLOCK 排第一 | 占 DB time | 判定 |
|---|---|---|---|
| L2 | `BufferContentLock`（35 万次 / 20.5 秒） | 10.5% | `WAIT_LWLOCK_HEAVY` |
| L3 | `ProcArrayLock`（310 万次 / 62 秒），其后 `CLogBufMappingLock`、`XidGenLock` | 16.0% | `WAIT_LWLOCK_HEAVY` |
| L4 | `LockMgrLock`（1073 万次 / 124 秒） | 18.3% | `WAIT_LWLOCK_HEAVY` |
| L5 | `XidGenLock`（27 万次）与 IO 里的 `SLRUWrite` / `SLRUFlushSync`；**没有** `SubtransControlLock` / `CLogControlLock` | 约 1% | 只有 `DBTIME_CPU_HEAVY` |

L5 是改不动的那一段：这个内核上判断子事务可见性不经过 `SubtransControlLock`，
4 核 3 会话也压不出多少争用。填 `actual` 时按上表能看到的东西判，不要替它圆场。
自证（连采 20 次）对 L2 这种微秒级的页锁几乎采不到（60 次里 1 次），**以快照窗口的累计为准**。

**轻量锁和普通锁完全是两回事：** 普通锁保护**数据**，能在 `pg_locks` 里看到谁锁了哪张表；
轻量锁保护内核自己的**共享内存结构**，持有时间以微秒计，**在 `pg_locks` 里一行都没有**，
只出现在等待事件统计里。所以这五段是专门用来检验 waitevent / wdr 的：
一个只会查 `pg_locks` 的工具，在这五段里会一律报「没有锁等待，库很正常」。

**五段的边界与 WDR 快照严格对齐**（0/240/480/720/960/1200 秒），
这样每个快照窗口里只有一种轻量锁争用，WDR 的多窗口分解才能给出
「这 4 分钟是谁在争、下 4 分钟换成了谁」。

> **可能不明显：** og5 只有 4 核、每段只开 3 条会话，改过之后的 L2–L5 也可能只是轻微争用。
> 这是环境限制，不是场景写错了。自证会写「真在等的 N 次，其中轻量锁 M 次」——`none`（在 CPU 上跑）
> 与 `wait cmd`（等客户端发命令）都**不算**在等；`status` 也会如实报出当下排名靠前的等待事件。
> 没争起来就是没争起来，不要替它圆场。

**轻量锁必须看累计统计，不能查一次就下结论。** 它的持有时间以微秒计，单次采样几乎总是
落在「没在等」的那一刻。本工具的自证因此改成连采 20 次（约 2 秒）再汇总——
实测 L1 这样能稳定看到 60 次观测里有 28~36 次在等 `WALFlushWait`，
而单次采样一直报「none」，看起来像场景没生效。
**这同时也是对工具的一条要求**：轻量锁要从 WDR 的等待事件段去看，
查一次 `pg_thread_wait_status` 是不够的。

## 4. 一次运行的时间线

| 阶段 | 时长 | 做什么 |
|---|---|---|
| 准备 | 几秒（第一次约 2 分钟） | 补建缺的运行期对象、把 `import_stage` 的表级参数设到位（§2） |
| 基线 | 1 分钟 | 打一个 WDR 快照 → 静默 → 再打一个。给 WDR 一个干净的对照窗口 |
| 故障窗口 | **20 分钟** | 按排期起场景；每 4 分钟一个 WDR 快照；每分钟一行进度 + 逐场景自证 |
| 收工 | 约 1 分钟 | 停场景（取消还挂着的语句）→ 打快照 → 清理 → 核对残留 |
| 恢复 | 1 分钟 | 静默 → 打最后一个快照（看库是否回到正常） |

同时吃 CPU 的会话峰值 **11 条**（上限 12，`check` 会算给你看）。og5 是 4 核，
这是约 3 倍超配：库明显卡，但没被压垮。再高就全是 CPU 排队，那时每个场景都「慢」，
反而分不出是谁造成的。

## 5. 安全边界

- **只动** 目标库里模式 `fl` 下的对象和用户 `fl_app`。其他模式（`demo_mem`、`perf_sim`、
  `gaussdb` 等）一个都不碰。
- **不改任何实例级参数**。所有超时、`work_mem`、`query_dop`、`synchronous_commit`（L2/L3 的异步提交）
  都是会话级；autovacuum 的调整都是表级，清理时还原——只有 `import_stage` 的
  「关 autovacuum + analyze 触发线拉满」是这张表的设计、一直留着（它本来就只给 V7/S5 用）。
- **动手前核对实例指纹**（容器内端口 + `version()`），对不上直接拒绝执行。

### 三道保险（故障不会比实验活得久）

1. 每条会话自带会话级超时：`statement_timeout` / `idle_in_transaction_session_timeout`
   是窗口 + 10 分钟；**`lockwait_timeout` 按场景自己的时段 + 1 分钟**（K3 是 130 + 60 秒，
   跟窗口一起结束的是剩余窗口 + 60 秒）——编排器被 kill 也会自己到期，等锁的语句也拖不过自己的时段；
2. 停场景时**取消还挂着的语句**：置停止位 → 等 2 秒 → 还在跑的 `pg_cancel_session` →
   再等 3 秒 → 还在的 `pg_terminate_session`。只认 `application_name` 恰好是那条会话的 `fl:` 会话，
   工具自己的连接（`fl:runner` / `fl:status` / `fl:stop` …）一律不碰。会跑完的慢 SQL（S3–S6）
   按排期停时不打断最后一轮，窗口结束时照样取消；
3. 看门线程：窗口结束后再等 10 分钟，无论主流程在干什么都强制收；
4. 收工后逐项核对残留，核不干净就**非 0 退出**，不让人以为「跑完了就干净了」。

**观测者自己不排队：** `status`、编排器自己的连接、停场景用的连接都带观测级超时
（等锁 3 秒、单条 30 秒）。哪一项被 DDL / VACUUM FULL 挡住，就写「这一项没查出来」，
不再陪着排进锁队列（2026-10-24 那轮 `status` 的 `pg_total_relation_size` 就排在 K3 的 ALTER 后面挂住过）。
`cleanup` 的连接等锁最多一分钟，VACUUM FULL 不限时长。

### 清理的两档

```bash
$P tools/faultlab/faultlab.py cleanup        # 回到「数据已备好」，下次可直接 run
$P tools/faultlab/faultlab.py purge --yes    # 连数据与用户一起删，库回到装这套之前
```

`cleanup` 会：杀掉 `fl:` 开头的会话 → 回滚两阶段事务 → 删复制槽 → 还原表级参数 →
删跑中途加的列和索引 → 清空运行期写入的表 → **回到库里实地核对一遍**还剩什么。

**登记过的残留按实际情况报：** 先看在不在，不在就写「不存在（那条 ALTER 没做成），不用删」，
在就撤、撤完再查一遍。以前一律报「已删」——2026-10-24 那轮 K3 的 ALTER 被取消、列根本没加上，
清理还写着「已删列」。撤了还在的不从登记簿划掉，下次清理接着收。

**不会自动撤销的影响**（每次运行都会留下，手册照实说明）：

| 影响 | 说明 |
|---|---|
| `pg_stat_database.deadlocks` 累计 +35 左右 | 这个计数不会自己清零，之后每次巡检都会看到 |
| Top SQL / 慢 SQL 的累计统计里混入实验 SQL | 要清只能 `reset_unique_sql`，代价是别的测试数据也一起丢 |
| 多出约 8 个 WDR 快照 | 保留 8 天后自动过期 |
| 时间线文件 `~/.faultlab/timeline.jsonl` | 故意留着供事后对照；下一次 run 会覆盖 |

## 6. 排查

### 跑完报「残留：…」

先看是什么。真会话残留多半是某条会话挂在锁等待里没退——再跑一次 `cleanup` 即可。
两阶段事务和复制槽一定要清掉：前者卡住回收水位，后者让 WAL 只增不删。

### 场景按排期停了，它的 SQL 还挂在库里 / 别的东西被堵住

停场景会取消还挂着的语句；时间线上那一行会写「停 K3  按排期结束;取消了 1 条挂着的语句」。
如果写的是「终止了 N 条会话」，说明取消没叫醒它，是直接断的连接；
如果写的是「N 条让它跑完这一轮」，那是 S3–S6 的最后一轮慢 SQL（故意的，见 §3.1）。
万一停场景那一步自己失灵，会话级 `lockwait_timeout` 也会在该场景时段结束后一分钟把等锁的语句掐掉。
这两样都没起作用时才需要人工：`faultlab.py cleanup`，或者只取消那一条——
**只动 `fl:` 开头、`application_name` 对得上的会话**。

### `status` 里写「这一项没查出来：等锁超过 3 秒…」

这一项要读的某张表上正排着 DDL 或 VACUUM FULL（K3 的 ALTER、V6 的 VACUUM FULL、K5 的建索引），
`status` 不陪它排队，先跳过这一项，别的项照常出。过一会儿再看，或者正好拿来核对「锁队列真的造出来了」。

### `status` 里看到一堆 `sessionid=0` 的条目

**这不是残留。** og5 开了线程池，`pg_stat_activity` 里会列出空闲的**工作线程**：
`sessionid = 0`、没有 `client_port` 和 `backend_start`，`application_name` 还留着
它上一次服务过的那个会话的名字。它们**不持任何锁**，`pg_terminate_backend` 对它们
返回成功但条目不会消失。

2026-10-17 实测踩过这个坑：所有连接都关了（`lsof` 看 5433 上一条 TCP 都没有），
`pg_stat_activity WHERE application_name LIKE 'fl:%'` 仍然返回 10 行，看起来像
「杀不掉的残留会话」。本工具因此一律只数 `sessionid <> 0` 的真会话。
**顺带值得核对的一点：** 如果某个 skill 把这些条目算进「连接数 / 活跃会话数」，会虚高一截。

### 慢 SQL 两秒就跑完了 / 一直跑不完

规模没校准，或者换了机器。重跑 `calibrate`。它的做法是：用很小的规模实测出
「每行外层大约多少毫秒」，再按目标耗时折算，结果写进 `~/.faultlab/caps.json`。

K5 的建索引、V6 的 VACUUM FULL 太快或太慢，调的是 `lab/config.py` 里的 `K5_SLOW_ITERS` /
`V6_SLOW_ITERS`（慢表达式每行做几轮 md5）。太慢没关系——时段一到会被取消；
太快的话 K5 的自证会写「索引提前建完了」，V6 会一次接一次地做（时间线上每做完一次记一行耗时）。

### 跑到一半 og5 自己重启了

2026-10-17 第三次全量跑时出过一次：先是宿主机上的命令开始报
`Too many open files in system`，紧接着 **og5 容器重启**（`pg_postmaster_start_time` 变新）。
好在只有 og5 重启，同一台机器上 k8s 那些容器都没事，og5 里的数据也完好。

原因是 macOS 的文件表（vnode 表）被打满：当时 S6 的 `work_mem` 设成 64kB，
四个排序各要切成极多的临时文件反复归并，再叠上沙箱虚拟机本身缓存着的大量文件句柄，
`kern.num_vnodes` 撞到了 `kern.maxvnodes`。

已经做的事：把 S6 的 `work_mem` 调到 2MB、S2 调到 4MB——照样是 external merge、
照样落几百 MB，但临时文件数少一个量级。**不要再把它们往下调。**

如果还是撞上：`sysctl vfs.vnstats.num_free_vnodes kern.num_files kern.maxfiles` 看余量。
（`kern.num_vnodes` 是已分配数，满了之后释放的 vnode 只进空闲表、不归还 —— 2026-10-24 实测
`num_deallocedvnodes=0`，它会一直等于 `kern.maxvnodes`，看它判断不了满没满。）
余量不够就先找出占着文件句柄的进程（`lsof -n -p <pid> | wc -l`）。
这台机器上占得最多的往往是沙箱虚拟机，在沙箱里 `sync; sudo sh -c 'echo 2 > /proc/sys/vm/drop_caches'`
能立刻放掉一大批。`kern.maxvnodes` 要 root 才能改，一般不动它。

**重启之后不用手工收拾**：那次的复制槽和两个两阶段事务都还在，
`cleanup` 从 `~/.faultlab/state.json` 里读出来，一次就全清掉了（残留：无）。

### WDR 快照失败

快照走容器里的 `omm`。实验用户即使有 SYSADMIN 也会报
`permission denied for schema snapshot`（`snapshot` 模式归初始用户所有）——
所以要能跑 `docker exec`。快照打不上不影响造故障，只是 WDR 对不上窗口。

## 7. 跑完之后：怎么用它检验 skill

1. `report` 拿到各场景的起止时刻（数据库时间）和快照号。
2. 对着 `expected.yaml` 一项项跑 skill，把实际结果填进 `actual` 字段。
   每个场景、每个跨场景项都已经留好了 `actual: ""`（空串 = 还没填）。填的时候写**一段文字**：
   哪个 skill 报了什么判定码、关键的一句话；没报也写明「未报」——不要写成列表，也不要删掉这个键。
3. **填之前先确认故障真的造出来了**：看 `signals` 那一列，用 `status` 复核。
   「skill 没报」有两种可能——它漏报，或者故障根本没造出来。分不清就等于没测。
4. 填完跑一次 `$P tools/faultlab/faultlab.py expected`（不连库）：核对 YAML 还读得通、每项都有 `actual`、
   场景编号与 `lab/config.py` 的排期表一一对应，并列出还剩哪几项没填。格式有问题时退出码 1。
   **以 `*` `&` `!` 等符号开头的值要加引号**——否则整份文件解析不了（S7 那一行原先就是这样）。

### 给模型的测试提问（对话里直接说，看它选不选对 skill、结论对不对）

- 「库现在很卡，帮我看看怎么了」→ 应该先做健康检查，而不是直接猜。
- 「有条 SQL 卡住了，谁把它挡住了？」→ K1：根阻塞会话应指到 `fl:K1/root`，不是链条中间的。
- 「这张表的死元组为什么清不掉？」→ V2/V3/V4：要能分清是长事务、两阶段事务还是复制槽。
- 「最近 20 分钟库里在等什么？」→ 轻量锁五段：应按窗口说出不同的争用，而不是一锅粥。
- 「哪条 SQL 最耗资源？」→ 总耗时榜应是 S7，平均耗时榜应是 S3/S4，两张榜不该相同。
- 「`fl.import_stage` 这张表的查询为什么这么慢？」→ 应指向统计信息过期，而不是只建议加索引。
- 「分析 <故障窗口的起止时刻> 这段时间的 WDR」→ 应能用 `snaps --from/--to` 定出窗口。

## 8. 改这套东西时要注意

- **排期表在 `lab/config.py`**，三条规矩写在注释里：CPU 预算不超上限、轻量锁按快照边界切、
  吃 CPU 的锁/VACUUM 场景彼此不重叠。改完跑 `check` 看 CPU 峰值。
- **每个场景都必须能自证**（`probe()`）。没有它，「场景生效了」和「场景悄悄失败了」
  在终端上长得一模一样，而人往往要等到用 skill 查不出东西时才发现。
- **不会自己消失的东西必须登记进 `state`**（两阶段事务、复制槽、表级参数、加的列和索引），
  否则下一次运行会带着上一次的残留开始，现象看起来还一模一样。**先登记、再动手**——
  建到一半被打断也有人收；清理时按库里实际在不在报结果。
- **场景的会话一律用 `self.worker(...)` 开**：它会按场景时段收紧等锁上限，停场景时也能被取消。
  自己 `Conn(...)` 开的连接不归 Worker 管、停场景时不会被取消，要自己给 `lockwait_s`
  （死锁场景撞车用的短命连接就是这么做的）。会跑完、要进执行历史的慢 SQL 用 `drain=True`。
- **场景之间别抢同一批行 / 同一张表**：K2 原来和 K1 抢 `acct` 的 1~3 号行，抖动型变成了持续阻塞；
  K5 的 DROP INDEX 排在 S2 的长查询后面，变成了 K3。加场景前先看一眼别的场景动了哪些行和表。
- **运行期对象**（慢表达式函数、`maint_hist`、`xact_tick`、`subx_log`、ustore 的 `hotpage`）
  的建法在 `prepare.runtime_ddl`，`run` 开跑前「有就不动、没有就补」，`prepare` 整个重建。
  改了 `K5_SLOW_ITERS` / `V6_SLOW_ITERS` 之后，`maint_hist` 的索引会在下一次 `run` 时按新轮数重建。
- **schema.sql 里有几处故意不建索引**（`payments.order_id`、`orders.cust_code`），
  它们是 S1/S3/S4/S5/S7 的成因，不是遗漏。
