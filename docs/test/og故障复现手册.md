# og 故障复现手册（faultlab）

在 openGauss 测试库上**一条命令造出 34 项典型性能问题、持续 20 分钟，再一条命令清干净**，
可以反复跑。用来检验这套 `gaussdb-*` 诊断 skill：面对已知的故障，它们报不报、报得对不对。

工具在 `tools/faultlab/`，预期发现矩阵在 `tools/faultlab/expected.yaml`。

> **只在测试库上跑。** 它会关掉表级 autovacuum、建复制槽、留孤儿两阶段事务、做 VACUUM FULL。
> 启动前会核对实例指纹，对不上就拒绝执行；但请不要去改那道核对。

---

## 1. 前置条件

| 要求 | 说明 |
|---|---|
| 目标库 | openGauss 测试实例。默认按 og5 配好：容器名 `og5`，Mac 上 `127.0.0.1:5433`，库 `postgres` |
| 解释器 | 要装了 `psycopg2`。Mac 上用 `~/p2venv/bin/python` |
| 容器可执行 | 建专用用户与打 WDR 快照要 `omm` 权限，经 `docker exec` 完成，所以要能跑 `docker` |
| 磁盘 | 数据约 900 MB；跑的过程中临时文件与 WAL 另算，留 5 GB 余量 |
| 宿主机文件表 | 落盘类场景（S2/S6）会产生大量临时文件。**macOS 上先确认文件表没被占满**：`sysctl kern.num_vnodes kern.maxvnodes`，两者相等就说明已经满了，这时不要开跑（见 §6 最后一条） |

换别的实例：在 `~/.faultlab/conn.json` 里写覆盖值（只写要改的字段）。

```json
{ "host": "127.0.0.1", "port": 5433, "dbname": "postgres", "container": "og5" }
```

## 2. 快速开始

```bash
cd ~/gh_skill/opencode_skill-main-v2-0729
P=~/p2venv/bin/python

$P tools/faultlab/faultlab.py check       # 环境自检，只读，不改任何东西
$P tools/faultlab/faultlab.py prepare     # 建用户 + 造数据，约 15 秒，**一次就够**
$P tools/faultlab/faultlab.py calibrate   # 校准慢 SQL 规模，约 20 秒，**换机器后跑一次**
$P tools/faultlab/faultlab.py run         # 造故障：1 分钟基线 + 20 分钟故障 + 清理 + 1 分钟恢复
```

跑的过程中**另开一个终端**看现象：

```bash
$P tools/faultlab/faultlab.py status --watch 10
```

跑完之后出报告（各场景的起止时刻、快照号，拿去对 WDR 窗口和 skill 输出）：

```bash
$P tools/faultlab/faultlab.py report
```

**建议用 `nohup` 跑 `run`**，这样终端断了也不影响（故障会按窗口自己结束）：

```bash
(nohup $P tools/faultlab/faultlab.py run > /tmp/faultlab.log 2>&1 &)
tail -f /tmp/faultlab.log
```

### 只跑一类

```bash
$P tools/faultlab/faultlab.py run --only lock,deadlock --window 600
```

分类：`slow`（慢 SQL）、`lock`（锁等待）、`deadlock`（死锁）、`vacuum`、`lwlock`（轻量锁）。
**全部一起跑** 时各类现象会互相影响（库整体变卡），这是故意的——现场就是这样。
要拿干净信号做单项验证时用 `--only`。

## 3. 34 项场景

### 3.1 慢 SQL（S1–S7）

每条 5~7 张表、多层嵌套。SQL 原文在 `tools/faultlab/sql/slow/*.sql`，每个文件开头写明了成因。

| 编号 | 造的是什么 | 怎么慢的 | 窗口内 |
|---|---|---|---|
| S1 | 相关子查询逐行执行 | `payments.order_id` 没索引，每取一行订单扫两遍百万行表 | **跑不完**（设计如此） |
| S2 | 三层派生表 + `LIKE` 前缀关联 | 前缀来自另一张表的列，索引用不上；外加 1MB work_mem 下哈希聚合落盘 | **跑不完** |
| S3 | `NOT IN` 碰上可空列 | 不能改写成反连接，退化成逐行子计划 | 约 8 分钟跑完 |
| S4 | 索引列上套类型转换 | `c.code::bigint = o.cust_id`，`idx_customers_code` 失效 | 约 3 分钟跑完 |
| S5 | 统计信息过期 + 数据倾斜 | 估 3 行、实际 16 万行，选了嵌套循环 | 约 8 分钟跑完 |
| S6 | 四个窗口函数 + 64kB work_mem | 每次排序都落盘，实测四个排序各落 77~112 MB | 约 30 秒一次，循环 |
| S7 | 高频点查 | `cust_code` 没索引，每次全表扫；单次零点几秒，靠**次数**堆出总耗时 | 一直跑 |

**S1/S2 与 S3–S6 的分工，是这一类的关键：**

- **S1/S2 一直跑不完** → 造的是「现在有一条 SQL 已经跑了十几分钟」。
  看它的是 health / lockwait / waitevent——它们读 `pg_stat_activity`，只看得到**正在执行**的。
- **S3–S6 会跑完** → 造的是「执行历史里有几分钟的 SQL」。
  看它的是 topsql / slowsql / wdr——它们读 `dbe_perf` 的统计，**只统计已完成的执行**，
  一直没跑完的 S1/S2 在那里一行都没有。
- **S7 高频** → 让「总耗时榜首」和「单条最慢」不是同一条。这两张榜本来就不该相同。

### 3.2 锁等待（K1–K10）

覆盖 `transactionid`、`tuple`、`relation`、`extend`、`advisory` 五种锁类型，以及「持锁者根本不在会话里」。

| 编号 | 造的是什么 | 现场的样子 |
|---|---|---|
| K1 | **四层**行锁阻塞链，根会话改完行后空闲不提交 | 杀链条中间那个解不开，必须杀最根上那个 |
| K10 | 孤儿两阶段事务：`PREPARE` 后会话退出 | **杀会话也解不开**——持锁者不在 `pg_stat_activity` 里 |
| K4 | 月结任务 `LOCK TABLE IN EXCLUSIVE MODE`，锁 2 分钟放 1 分钟 | 「每小时总有几分钟特别卡」，赶到时已经放开了 |
| K6 | 外键父子表互等 | 主数据维护与业务写入同时跑，两边都不觉得自己在加锁 |
| K7 | 多会话插同一个主键 | 等的是 `transactionid`，`pg_locks` 里看不到行锁 |
| K8 | 咨询锁（advisory）排队 | 没有任何表被锁，业务就是过不去 |
| K2 | 批处理 `FOR UPDATE` 分批锁行 | **抖动型**：瞬时查询常常什么都看不到，要看一段时间的统计 |
| K5 | 不带 `CONCURRENTLY` 建索引 | 白天「顺手加个索引」，这张表的写入全部超时 |
| K3 | **DDL 锁队列放大** | 一个只读长查询 + 一个加字段，把整张表的读写全冻住 |
| K9 | 并发插入抢表扩展锁 | 批量导入「越加并发越不快」 |

K3 最反直觉，也最值得用来检验工具：长查询本来谁也不挡，但 `ALTER TABLE` 要等它，
而 ALTER 已经在队列里排上了表级排他锁，**后面所有读写都得排在 ALTER 之后**。
根因是那个长查询，不是 ALTER——报错了对象，运维就会去杀错的会话。

### 3.3 死锁（D1–D6）

一个驱动会话轮流演六种形态，约 30 秒一次，20 分钟大约 35 次。

| 编号 | 形态 | 该给的建议 |
|---|---|---|
| D1 | 两会话交叉更新同表两行 | 统一加锁顺序 |
| D2 | 三会话成环 | 同上，但要能看出是环 |
| D3 | 跨表加锁顺序相反 | 统一表的访问顺序 |
| D4 | 锁升级：都先 `FOR SHARE` 再都 `UPDATE` | 一开始就 `FOR UPDATE` |
| D5 | 外键引起 | 调整父子表写入顺序 |
| D6 | 唯一索引按相反顺序插入 | 按序插入 / 批量前排序 |

D4 最隐蔽：两笔事务一开始「只是读」，代码里看不到任何交叉加锁的痕迹。

> **死锁牺牲者收到的报错是预期的**，不算运行失败。运行结束时统计的「出错的会话」
> 已经把这类预期报错排除了。

### 3.4 VACUUM（V1–V7）

这一类有一条贯穿的主线：**死元组清不掉的原因不止一个，而解法完全不同。**
诊断工具的价值就在于分清是哪一种——报一句「有死元组」等于没说。

| 编号 | 原因 | 解法 |
|---|---|---|
| V1 | autovacuum 被**关掉**了 | 开回去 |
| V5 | autovacuum **开着**，但被限速到追不上 | 调 `cost_delay` / `cost_limit` |
| V2 | 长事务持着旧快照 | 去找那笔事务；改 autovacuum 没用 |
| V3 | 两阶段事务 | `ROLLBACK PREPARED`——连会话都没有 |
| V4 | 复制槽没人消费 | 删槽或让备机跟上 |
| V6 | 业务高峰做 `VACUUM FULL` | 空间收回来了，代价是这张表读写全断 |
| V7 | 导入后不收集统计信息 | `ANALYZE`（它也是 S5 的成因） |

V1 与 V5 的区别最该被工具分清：V5 里 `last_autovacuum` 一直在更新，
**只看「autovacuum 开没开」会判成正常**。

### 3.5 轻量锁（L1–L5）

| 编号 | 造的是什么 | 预期等待事件 | 时间段 |
|---|---|---|---|
| L1 | 提交风暴：单行插入 + 每条即提交 | `WALInsertLock` / `WALWriteLock` / `WALFlushWait` | 0~4 分钟 |
| L2 | 热点页：反复更新 100 行的小表 | `BufferContentLock` | 4~8 分钟 |
| L3 | 极短事务高频提交 | `XidGenLock` / `ProcArrayLock` / CSN 相关 | 8~12 分钟 |
| L4 | 千分区表全分区扫描 | `LockMgrLock` | 12~16 分钟 |
| L5 | 每事务上千个子事务（`EXCEPTION` 块） | `SubtransControlLock` / CLog 相关 | 16~20 分钟 |

**轻量锁和普通锁完全是两回事：** 普通锁保护**数据**，能在 `pg_locks` 里看到谁锁了哪张表；
轻量锁保护内核自己的**共享内存结构**，持有时间以微秒计，**在 `pg_locks` 里一行都没有**，
只出现在等待事件统计里。所以这五段是专门用来检验 waitevent / wdr 的：
一个只会查 `pg_locks` 的工具，在这五段里会一律报「没有锁等待，库很正常」。

**五段的边界与 WDR 快照严格对齐**（0/240/480/720/960/1200 秒），
这样每个快照窗口里只有一种轻量锁争用，WDR 的多窗口分解才能给出
「这 4 分钟是谁在争、下 4 分钟换成了谁」。

> **可能不明显：** og5 只有 4 核、每段只开 3 条会话，L4 / L5 的争用可能很轻。
> 这是环境限制，不是场景写错了。`status` 会如实报出当下排名靠前的等待事件——
> 没争起来就是没争起来，不要替它圆场。

**轻量锁必须看累计统计，不能查一次就下结论。** 它的持有时间以微秒计，单次采样几乎总是
落在「没在等」的那一刻。本工具的自证因此改成连采 20 次（约 2 秒）再汇总——
实测 L1 这样能稳定看到 60 次观测里有 28~36 次在等 `WALFlushWait`，
而单次采样一直报「none」，看起来像场景没生效。
**这同时也是对工具的一条要求**：轻量锁要从 WDR 的等待事件段去看，
查一次 `pg_thread_wait_status` 是不够的。

## 4. 一次运行的时间线

| 阶段 | 时长 | 做什么 |
|---|---|---|
| 基线 | 1 分钟 | 打一个 WDR 快照 → 静默 → 再打一个。给 WDR 一个干净的对照窗口 |
| 故障窗口 | **20 分钟** | 按排期起场景；每 4 分钟一个 WDR 快照；每分钟一行进度 + 逐场景自证 |
| 收工 | 约 1 分钟 | 停场景 → 打快照 → 清理 → 核对残留 |
| 恢复 | 1 分钟 | 静默 → 打最后一个快照（看库是否回到正常） |

同时吃 CPU 的会话峰值 **11 条**（上限 12，`check` 会算给你看）。og5 是 4 核，
这是约 3 倍超配：库明显卡，但没被压垮。再高就全是 CPU 排队，那时每个场景都「慢」，
反而分不出是谁造成的。

## 5. 安全边界

- **只动** 目标库里模式 `fl` 下的对象和用户 `fl_app`。其他模式（`demo_mem`、`perf_sim`、
  `gaussdb` 等）一个都不碰。
- **不改任何实例级参数**。所有超时、`work_mem`、`query_dop` 都是会话级；
  autovacuum 的调整都是表级，清理时还原。
- **动手前核对实例指纹**（容器内端口 + `version()`），对不上直接拒绝执行。

### 三道保险（故障不会比实验活得久）

1. 每条会话自带会话级超时（`statement_timeout` / `idle_in_transaction_session_timeout` /
   `lockwait_timeout`，都是窗口 + 10 分钟）——编排器被 kill 也会自己到期；
2. 看门线程：窗口结束后再等 10 分钟，无论主流程在干什么都强制收；
3. 收工后逐项核对残留，核不干净就**非 0 退出**，不让人以为「跑完了就干净了」。

### 清理的两档

```bash
$P tools/faultlab/faultlab.py cleanup        # 回到「数据已备好」，下次可直接 run
$P tools/faultlab/faultlab.py purge --yes    # 连数据与用户一起删，库回到装这套之前
```

`cleanup` 会：杀掉 `fl:` 开头的会话 → 回滚两阶段事务 → 删复制槽 → 还原表级参数 →
删跑中途加的列和索引 → 清空运行期写入的表 → **回到库里实地核对一遍**还剩什么。

**不会自动撤销的影响**（每次运行都会留下，手册照实说明）：

| 影响 | 说明 |
|---|---|
| `pg_stat_database.deadlocks` 累计 +35 左右 | 这个计数不会自己清零，之后每次巡检都会看到 |
| Top SQL / 慢 SQL 的累计统计里混入实验 SQL | 要清只能 `reset_unique_sql`，代价是别的测试数据也一起丢 |
| 多出约 8 个 WDR 快照 | 保留 8 天后自动过期 |
| 时间线文件 `~/.faultlab/timeline.jsonl` | 故意留着供事后对照；下一次 run 会覆盖 |

## 6. 排查

### 跑完报「残留：…」

先看是什么。真会话残留多半是某条会话挂在锁等待里没退——再跑一次 `cleanup` 即可。
两阶段事务和复制槽一定要清掉：前者卡住回收水位，后者让 WAL 只增不删。

### `status` 里看到一堆 `sessionid=0` 的条目

**这不是残留。** og5 开了线程池，`pg_stat_activity` 里会列出空闲的**工作线程**：
`sessionid = 0`、没有 `client_port` 和 `backend_start`，`application_name` 还留着
它上一次服务过的那个会话的名字。它们**不持任何锁**，`pg_terminate_backend` 对它们
返回成功但条目不会消失。

2026-10-17 实测踩过这个坑：所有连接都关了（`lsof` 看 5433 上一条 TCP 都没有），
`pg_stat_activity WHERE application_name LIKE 'fl:%'` 仍然返回 10 行，看起来像
「杀不掉的残留会话」。本工具因此一律只数 `sessionid <> 0` 的真会话。
**顺带值得核对的一点：** 如果某个 skill 把这些条目算进「连接数 / 活跃会话数」，会虚高一截。

### 慢 SQL 两秒就跑完了 / 一直跑不完

规模没校准，或者换了机器。重跑 `calibrate`。它的做法是：用很小的规模实测出
「每行外层大约多少毫秒」，再按目标耗时折算，结果写进 `~/.faultlab/caps.json`。

### 跑到一半 og5 自己重启了

2026-10-17 第三次全量跑时出过一次：先是宿主机上的命令开始报
`Too many open files in system`，紧接着 **og5 容器重启**（`pg_postmaster_start_time` 变新）。
好在只有 og5 重启，同一台机器上 k8s 那些容器都没事，og5 里的数据也完好。

原因是 macOS 的文件表（vnode 表）被打满：当时 S6 的 `work_mem` 设成 64kB，
四个排序各要切成极多的临时文件反复归并，再叠上沙箱虚拟机本身缓存着的大量文件句柄，
`kern.num_vnodes` 撞到了 `kern.maxvnodes`。

已经做的事：把 S6 的 `work_mem` 调到 2MB、S2 调到 4MB——照样是 external merge、
照样落几百 MB，但临时文件数少一个量级。**不要再把它们往下调。**

如果还是撞上：`sysctl kern.num_vnodes kern.maxvnodes` 看是不是满了。
满了就先找出占着文件句柄的进程（`lsof -n -p <pid> | wc -l`）。
这台机器上占得最多的往往是沙箱虚拟机，在沙箱里 `sync; sudo sh -c 'echo 2 > /proc/sys/vm/drop_caches'`
能立刻放掉一大批。`kern.maxvnodes` 要 root 才能改，一般不动它。

**重启之后不用手工收拾**：那次的复制槽和两个两阶段事务都还在，
`cleanup` 从 `~/.faultlab/state.json` 里读出来，一次就全清掉了（残留：无）。

### WDR 快照失败

快照走容器里的 `omm`。实验用户即使有 SYSADMIN 也会报
`permission denied for schema snapshot`（`snapshot` 模式归初始用户所有）——
所以要能跑 `docker exec`。快照打不上不影响造故障，只是 WDR 对不上窗口。

## 7. 跑完之后：怎么用它检验 skill

1. `report` 拿到各场景的起止时刻（数据库时间）和快照号。
2. 对着 `expected.yaml` 一项项跑 skill，把实际结果填进 `actual` 字段。
3. **填之前先确认故障真的造出来了**：看 `signals` 那一列，用 `status` 复核。
   「skill 没报」有两种可能——它漏报，或者故障根本没造出来。分不清就等于没测。

### 给模型的测试提问（对话里直接说，看它选不选对 skill、结论对不对）

- 「库现在很卡，帮我看看怎么了」→ 应该先做健康检查，而不是直接猜。
- 「有条 SQL 卡住了，谁把它挡住了？」→ K1：根阻塞会话应指到 `fl:K1/root`，不是链条中间的。
- 「这张表的死元组为什么清不掉？」→ V2/V3/V4：要能分清是长事务、两阶段事务还是复制槽。
- 「最近 20 分钟库里在等什么？」→ 轻量锁五段：应按窗口说出不同的争用，而不是一锅粥。
- 「哪条 SQL 最耗资源？」→ 总耗时榜应是 S7，平均耗时榜应是 S3/S4，两张榜不该相同。
- 「`fl.import_stage` 这张表的查询为什么这么慢？」→ 应指向统计信息过期，而不是只建议加索引。
- 「分析 <故障窗口的起止时刻> 这段时间的 WDR」→ 应能用 `snaps --from/--to` 定出窗口。

## 8. 改这套东西时要注意

- **排期表在 `lab/config.py`**，三条规矩写在注释里：CPU 预算不超上限、轻量锁按快照边界切、
  吃 CPU 的锁/VACUUM 场景彼此不重叠。改完跑 `check` 看 CPU 峰值。
- **每个场景都必须能自证**（`probe()`）。没有它，「场景生效了」和「场景悄悄失败了」
  在终端上长得一模一样，而人往往要等到用 skill 查不出东西时才发现。
- **不会自己消失的东西必须登记进 `state`**（两阶段事务、复制槽、表级参数、加的列和索引），
  否则下一次运行会带着上一次的残留开始，现象看起来还一模一样。
- **schema.sql 里有几处故意不建索引**（`payments.order_id`、`orders.cust_code`），
  它们是 S1/S3/S4/S5/S7 的成因，不是遗漏。
- 单元测试在 `tests/test_faultlab_units.py`（纯函数：排期预算、SQL 规模校验、残留登记簿、
  报告渲染），不连库，随仓库全量测试一起跑。
