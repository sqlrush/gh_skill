## 附录 A：需跨用例对比才成立的两项证据

单看一条用例得不出结论，这两项要放在一起读。

### A-1　文本替换在标识符位真的生效（5.3a vs 5.3b）

同一条脚本 `select ... from pg_stat_activity order by {{sort_col}} desc limit {{limit}}`，
只换 `sort_col` 的取值：

| sort_col | 返回的 usename 顺序 |
|---|---|
| `backend_start` | `['gaussdb', 'gaussdb', 'gaussdb']` |
| `usename` | `['omm', 'omm', 'omm']` |

**两次结果不同 = True**

若改用绑定变量实现，`ORDER BY $1` 会**按常量排序（等于不排序）**，
两次结果将完全相同、且不报错 —— 这正是本实现不用绑定变量的原因：
一条在客户环境跑得好好的脚本，在本地会安静地给出错误结果。

### A-2　String 参数可被注入（5.2a vs 5.2b）

同一条脚本 `where usename = '{{username}}'`：

| username 取值 | 返回行数 |
|---|---|
| `no_such_user_zz9` | **0** |
| `no_such_user_zz9' or '1'='1` | **23** |

渲染过程：

```
where usename = 'no_such_user_zz9' or '1'='1'      ← 条件恒真，返回全表
```

**这是设计上接受的结果，不是缺陷。** 客户中间件若同样用 `String.replace`
实现（最简的 Java 写法），客户环境存在同一个洞。注册工具会把这类脚本
标为 `STRING_PARAM` 风险，摆到台面上由人决策。

**需向客户确认：GRMP 对 String 参数是否做转义或绑定。**
若不做，其现有脚本库里所有带 String 参数的脚本都有同样问题。
