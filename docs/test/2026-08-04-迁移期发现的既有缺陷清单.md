# gh_skill 迁移期发现的既有缺陷清单

**日期**：2026-08-04
**范围**：把 13 个 skill 的数据库访问方式改成「中间件 / 直连」双路径过程中，
顺带发现的**既有**问题。迁移本身引入的回归单独标注，不与既有缺陷混列。

判定「既有」的方法统一是 `git show 0d7b337:<file>`（客户改造版导入那一次提交），
不是凭印象。

---

## 一、已修（客户已确认或属于明确错误）

### 1. wdr collect 整条命令崩溃 —— 异常处理里自己抛异常

`skill_wdr_005` 的格式化串写了 `{c}`，而上下文里的变量叫 `e`。这句在
`except` 块**外面**，`KeyError` 没人接，`wdr collect` 直接整条崩。

不是「某个维度降级」，是命令不可用。

**状态**：已修（用户批准）。

---

### 2. collect_schema 静默返回空 —— 括号套了两层

`_SCHEMA_SYS_FILTER` 本身已经带括号，使用处又包了一层，拼出：

```sql
nspname NOT IN (('pg_catalog','information_schema',...))
```

openGauss 报 `arguments of row IN must all be row expressions`。
而调用方把这个异常当成「查不到」处理，于是**schema 信息永远是空的，
却没有任何提示**。

**状态**：已修。

---

### 3. proctune 的 IN 列表把 Python list 直接拼进了 SQL

`evidence.py` 用 `.format(names=table_names)` 拼 `IN (...)`，`table_names`
是 Python list，拼出来是：

```sql
WHERE relname IN ['orders', 'customers']
```

136 个游标里有 100 个走这条路径，全是坏的。

**状态**：已修（与 sqltune 的写法对齐）。

---

### 4. health 的 SQL 里粘进了 Python 源码

`skill_health_008` 的字符串字面量中间粘了一段 Python 代码。

**状态**：已修（用户批准）。

---

### 5. 三个测试文件自客户版导入起从未执行过

`test_health_units.py` / `test_procfamily_units.py` / `test_sqlfamily_units.py`
里写的路径是 `skills/<name>/scripts`，真实目录是 `skills/gaussdb-<name>/scripts`。

后果比「几条测试没跑」严重：**收集阶段就 FileNotFoundError，会中断整个
`pytest tests/`**。也就是说这个仓库的「跑全量测试」这件事本身一直是坏的，
只是没人在 CI 里跑过。看着有 24 条覆盖，实际一条没执行。

**状态**：已修。修好后全量从 599 → 636 passed。

---

### 6. `test_state_dir_defaults_to_dot_gdaa` 自导入起一直是红的

客户把状态目录默认值从 `~/.gdaa` 改成了容器内的 `/workspace/.opencode/skills/common`
（他们的 OpenCode 容器里这个路径一定存在），但没改测试。

**没有把默认值改回去** —— 那会破坏客户部署。改的是测试，让它断言真实契约。

⚠️ **顺带记一个坑**：在容器外（比如本机开发），`/workspace` 不存在、也建不出来
（根目录无写权限）。不设 `GSDB_HOME` 直接跑任何 skill，都会在写状态时失败。
本机开发/测试请 `export GSDB_HOME=$HOME/.gdaa`。

**状态**：已修（改测试，不改行为）。

## 二、已报告、按用户指示不修

```sql
WHERE t.n_dead_tup > 0+
```

**当前实测**（2026-08-04）：

```
执行脚本 health.bloat 失败：ERROR: syntax error at or near "AND" (SQLSTATE 42601)
```

这条自始至终没跑通过。也正因为它一直坏着、health 一直在降级，
才掩盖了同一段代码里的另一个问题（`x is None` 判 NULL，见第 10 条）——
那句 `float(x)` 从来没被执行到。

**状态**：**未修**（用户明确指示只报不修）。已在
`scripts/registry/health/bloat.yaml` 顶部写了醒目注释说明它是坏的。

## 三、已报告、需要你决定

### 8. sqltune 的 SKILL.md 说会话「始终只读」，但 `--analyze` 会开可写会话

`SKILL.md:123` 写的是：

> 脚本对数据库的会话是**只读**的（写/DDL 被会话级 `READ ONLY` 拦截）

而 `sqltune.py:214` 是：

```python
db = access.session_for(args.conn, read_only=not args.analyze)
```

带 `--analyze` 时会话就是可写的。后半句「对 DML 自动包在回滚事务里」是准确的，
所以**行为本身是对的、也是有意的**（EXPLAIN ANALYZE 一条 DML 必须真执行）。
不准确的是前半句那个括号里的绝对化说法。

给客户看的文档里出现「会话始终只读」这种承诺，是合规口径问题，不是技术问题。
**建议改文档措辞**，但改法取决于你想对客户怎么表述，我没动。

---

### 9. `extract_tables()` 丢掉 schema 限定

```
extract_tables("SELECT * FROM sales.orders o JOIN public.cust c ON 1=1")
  -> ['orders', 'cust']
```

后续拿这些名字去查 `pg_class`，同名不同 schema 的表会取错统计信息 ——
而且**不报错**，调优结论直接建立在别的表的数据上。

这是既有行为（docstring 里写明了 "schema-stripped"），改它会影响调优结论，
不是纯 bug 修复。**要不要改是你的判断**。

---

### 10. `key_gucs` 要 11 个参数，openGauss-lite 只返回 10 个

缺 `max_parallel_workers_per_gather`（lite 版没这个参数）。

不报错、不提示，报告里就是少一项。严格说这是**环境能力差异**不是缺陷，
但表现形式是静默的 —— 如果客户的正式版 GaussDB 也缺某个参数，
sqltune 会安静地少看一个维度。

**建议**：脚本按名字逐个校验，缺哪个就在报告里点名说「本实例无此参数」。
需要改 SQL + 报告渲染，**没做**，等你确认要不要。

## 四、迁移引入的回归（我造成的，已修）

单列出来是为了不和既有缺陷混在一起邀功。

### 11. `x is None` 在协议下永远不成立

中间件把 NULL 渲染成**空串**，不是 `None`。迁移前所有 `if x is None` 的分支
条件永不成立，后面那句 `float(x)` 抛 `ValueError`。

修：加 `common/grmp/values.py:is_null()`，修掉 4 处（health 的 autovacuum 时间 /
复制延迟 / bloat，wdr 的报告行过滤）。

不能写 `if not x` —— 那会把 0 当 NULL，而「距今 0 秒」与「从未发生」是两回事。

---

### 12. `--timeout` 被完全忽略（9 个 skill）

迁移前每个 skill 都调 `db.set_statement_timeout(args.timeout)`。改走
`access.for_conn()` 之后没人再往下传，参数照收、照进 `--help`，然后彻底失效。

**用户设 `--timeout 5`，查询照样能在客户生产库上一直跑，而且不报错。**

修：`access.for_conn(name, timeout=N)` 把值交给取数层；未指定时取 30 秒
（与迁移前各 skill 的 argparse 默认值一致 —— 迁移只该换通道，不该改超时行为）。

中间件路径**设不了**超时（协议没这个旋钮，注册脚本里也塞不进 `SET`，那是第二条
语句）。显式指定时在 stderr 说一声；没指定就不吭声，否则每次调用都刷一行，
提示很快就没人看了。

验证：直连 `SELECT pg_sleep(5)` 限 2 秒 → 2.0s 后 `SQLSTATE 57014` 掐断。

**为什么之前没发现**：双路径一致性检查比的是「两条链路输出一样不一样」，
两边都不设超时时，它们照样一样。已补 6 条测试，其中一条扫全仓 ——
任何声明了 `--timeout` 却不往下传的 skill 都会红。

---

### 13. 误提交了一条 `EXPLAIN {{sql}}` 直通脚本

`scripts/registry/proctune/explain_plan.yaml`。它等于在白名单上开一个通用入口，
任何 SQL 都能从这条脚本进去，白名单形同虚设。

原因是我用了两次 `git add -A`，把子代理正在处理中、且已决定删除的文件扫了进来。

修：`git rm --cached` 移除，并全仓核查确认白名单里不再有任何透传脚本：

```
grep -rlE '\{\{ *(sql|user_sql|query|stmt) *\}\}' scripts/registry/   # 无匹配
```

## 五、结构性风险（已加防护，不是缺陷）

### 14. 7 组脚本跨 skill 重复，共 19 个文件

`key_gucs`、`from_history`、`from_statement`、`proc_def`、`tables`、
`column_stats`、`version` 各有 2–4 份逐字相同的副本。

**不合并**是有意的：客户只能通过发布 DML 往 `script_config` 灌脚本，没有脚本
管理接口。各 skill 自带全套脚本，客户才能单独上线某一个 skill。

风险在于：在一份里修了 bug，另外几份还坏着 —— 第 3 条那个 IN 列表就是活例子。
双路径一致性检查发现不了，它比的是「同一条脚本走两条链路」，
不是「几条同源脚本彼此」。

**已加** `tests/test_registry_drift_units.py`：组内分叉就红，外加一条全仓扫描
（SQL 相同却没登记进名单的也红）。那条扫描当场就抓出我自己漏登记的 2 份。
