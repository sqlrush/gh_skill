# grmp-mock 测试方案（封装 og5）

**日期**：2026-08-03
**被测对象**：`tools/grmp_mock/`（GRMP 协议兼容中间件）+ `common/grmp/`（共用渲染层）+ `common/access.py`（skill 统一入口）
**后端库**：og5（openGauss-lite 5.0.3，`127.0.0.1:5433`）

---

## 怎么读这份方案

每条用例标了**证据等级**，它决定「这条通过了」意味着什么：

| 标记 | 含义 | 通过意味着 |
|---|---|---|
| 【实】 | 客户实际调用报文证实 | 与客户环境行为一致 |
| 【规】 | 接口文档明确规定 | 与文档一致（文档可能过时） |
| 【推】 | 由间接证据推断 | 与我们的推断一致，**不保证与客户一致** |
| 【发明】 | 文档零样例，本实现自定 | 只是自洽，**客户环境行为未知** |

**【推】和【发明】的用例即使全绿，也不能得出「客户环境能跑」的结论。**
它们的价值是保证行为稳定、可预期，而不是保证正确。

## 1. 启动横幅

### 1.1 横幅必须打出来 【发明】

启动后 stderr 应立刻出现横幅，含：

- `⚠️ 仅限本机开发调试。只监听 127.0.0.1`
- 脚本数 5、实例映射 1 条
- **「本进程当前的假设」** 六行，逐项列出取值

**为什么单独测**：横幅曾经因为走 stdout 被块缓冲而完全丢失（进程被 kill 时一个字都没落盘）。这是运行期唯一能看到「本进程按哪套未证实假设在跑」的地方，丢了等于没有。

**验证它真的会落盘**：

```bash
python3 -m tools.grmp_mock --port 8770 > /tmp/b.log 2>&1 &
sleep 1; kill %1; grep -c "本进程当前的假设" /tmp/b.log     # 期望 1
```

### 1.2 缺令牌拒绝启动 【发明】

```bash
env -u GRMP_AUTH_TOKEN python3 -m tools.grmp_mock --port 8771; echo "exit=$?"
```

期望：提示缺少 `GRMP_AUTH_TOKEN`，`exit=2`，**不启动**。

## 2. 注册工具（对应客户的版本 DML 发布）

### 2.1 正常注册与风险标注 【发明】

见 0.3。要点：`session.top_by` **被放行**而不是被拒。

**为什么不拒**：标识符位的占位符在客户的文本替换中间件上能正常跑。拒了就是本地比客户更严，会拒掉一条客户天天在跑的脚本，本地测试反而失去参照价值。

### 2.2 硬拦截：占位符未声明 【发明】

```bash
mkdir -p /tmp/bad/x && cat > /tmp/bad/x/a.yaml <<'EOF'
name: bad.undeclared
description: d
sql: |
  select * from t where a > {{n}} limit {{m}};
params:
  - key: n
    type: INTEGER
    description: x
EOF
python3 -m tools.grmp_register --registry /tmp/bad --db /tmp/bad.db; echo "exit=$?"
```

期望：`SQL 中的占位符未在 params 声明：m`，`exit=1`，**一条都不入库**。

### 2.3 硬拦截：声明了但 SQL 没用到 【发明】

把上面 YAML 改成 SQL 里只有 `{{n}}`、params 里多声明一个 `unused`。
期望：`params 声明了但 SQL 未使用：unused`。

**为什么这也要拦**：调用方会被迫传一个对 SQL 毫无影响的参数，属于定义错误。

### 2.4 重名保护 【发明】

```bash
python3 -m tools.grmp_register --db ~/.gdaa/grmp/script_config.db; echo "exit=$?"
```

期望：`注册中止：脚本 health.db_info 已注册（id=1）。要覆盖请显式指定 replace，否则会静默冲掉已在用的定义。`，`exit=1`

```bash
python3 -m tools.grmp_register --db ~/.gdaa/grmp/script_config.db --replace
```

期望：全部成功，**id 保持 1–5 不变**。

**为什么 id 必须不变**：调用方缓存「逻辑名 → id」的解析结果。换 id 会让缓存指向另一条脚本，表现为执行成功、结果无关、不报错。

### 2.5 导出交付 DML 【实】

```bash
python3 -m tools.grmp_register --db /tmp/t.db --dml-out /tmp/d.sql --user 12345678
head -20 /tmp/d.sql
```

逐项核对（对照客户样例 DML）：

- [ ] 表名 `grmp.grmp.script_config`（三段式）
- [ ] 21 列，列序与客户一致
- [ ] `"extend"` 带双引号，其余列不带
- [ ] `region` / `deployment_form` / `last_modify_time` 写 `NULL` 而非 `''`
- [ ] `refered_appbusiness` / `is_valid` / `is_asyn` 是裸整数，不带引号
- [ ] `create_user` 与 `last_modify_user` 同值，`last_modify_time` 为 NULL
- [ ] `create_time` 精确到毫秒
- [ ] SQL 正文里的单引号被翻倍（`(''template1'')`）
- [ ] `parameter_config` 形如 `[{"key":"…","value":"","type":"INTEGER","autoAcquire":false}]`，无空格

### 2.6 注册期不做语法校验 —— 已知缺口 【实】

```bash
mkdir -p /tmp/br/x && cat > /tmp/br/x/a.yaml <<'EOF'
name: broken.missing_table
description: 故意指向不存在的表
sql: |
  select * from a_table_that_does_not_exist_zz9;
EOF
python3 -m tools.grmp_register --registry /tmp/br --db /tmp/br.db; echo "exit=$?"
```

期望：**注册成功**（`exit=0`）。

**这是有意的**：客户没有注册期校验（脚本直接 INSERT 进表），语法错的脚本能进去、执行时才炸。我们照此复刻。代价是模板本身写错要到执行时才发现——这一点在开发方案里已记为待补项。

## 3. 接口一：查询命令列表

### 3.1 客户示例的报文格式 【实】

```bash
post "$B" '{"dataIp":"10.0.0.9","offset":1,"limit":10}'
```

期望：

- [ ] `code` 是**字符串** `"0"` 不是数字 0
- [ ] `msg` 为 `"success"`
- [ ] `result` 有 **18 个字段**（不只 total/list）
- [ ] `total` 为 5
- [ ] 每条详情的键恰好是 `id`/`cmd`/`cmd_name`/`description`/`cmd_type`/`param`
- [ ] `id` 是字符串
- [ ] `cmd` 含原始 `{{}}` 占位符
- [ ] `description` 与 `cmd_name` 相同
- [ ] 无参脚本的 `param` 是 `[]` 不是 `null`

### 3.2 PageInfo 的三个坑 【实】

```bash
post "$B" '{"dataIp":"10.0.0.9","offset":1,"limit":10}' | python3 -m json.tool | grep -E "navigate|prePage|nextPage|isFirst|isLast"
```

- [ ] 字段名是 `navigatepageNums`（**第二个 p 小写**），不是 `navigatePageNums`
- [ ] `navigatePages` 固定为 `8`
- [ ] `prePage` / `nextPage` 在边界处是 `0`，**不是 null**
- [ ] `isFirstPage` 等四个是真布尔值 `true/false`，不是字符串

### 3.3 offset 是页码不是行偏移量 【规】

```bash
post "$B" '{"dataIp":"10.0.0.9","offset":1,"limit":2}'
post "$B" '{"dataIp":"10.0.0.9","offset":2,"limit":2}'
```

期望：第 1 页给 id=1,2；第 2 页给 **id=3,4**（不是 id=2,3）。

**猜错的后果**：按行偏移量实现，翻到第二页取到错误数据段，且报文完全正常——不报错、只出错值。

### 3.4 省略 offset/limit 【实】

```bash
post "$B" '{"dataIp":"10.0.0.9"}'
```

期望：`pageNum=1`、`pageSize=10`。

### 3.5 不存在的 dataIp —— 逐字比对 【实】

```bash
post "$B" '{"dataIp":"1.2.3.4"}'
```

期望**一字不差**：

```json
{"code": "1", "msg": "通过dataIp查询不到对应高斯实例信息"}
```

- [ ] HTTP 状态码是 **200**（`curl -o /dev/null -w "%{http_code}"` 确认）
- [ ] 响应里**没有** `result` 键

**为什么重要**：客户把这次调用当作「接口鉴权与调用链路正常」的判据。

### 3.6 越界参数报错而不夹取 【发明】

```bash
post "$B" '{"dataIp":"10.0.0.9","offset":0}'
post "$B" '{"dataIp":"10.0.0.9","limit":0}'
post "$B" '{"dataIp":"10.0.0.9","limit":1001}'
post "$B" '{"dataIp":"10.0.0.9","offset":"x"}'
```

期望：四条都是 `code:"1"` 并说明范围。

**为什么不夹取**：夹取会静默改变调用方要的那一页，之后翻页逻辑全对不上而毫无征兆。

### 3.7 不支持服务端按类型过滤 【实】

```bash
post "$B" '{"dataIp":"10.0.0.9","cmd_type":"SQL"}'
```

期望：`code:"1"`，说明本接口不支持服务端过滤。

**为什么报错而不忽略**：默默忽略会让调用方以为服务端筛过了。客户端的 `--cmd-type` 是本地过滤。

## 4. 接口二：执行

### 4.1 五条脚本全跑通 【实】+【规】

```bash
post "$I" '{"dataIp":"10.0.0.9","id":"1"}'
post "$I" '{"dataIp":"10.0.0.9","id":"2","param":[{"param_name":"active_only","param_value":"true"},{"param_name":"limit","param_value":"5"}]}'
post "$I" '{"dataIp":"10.0.0.9","id":"3","param":[{"param_name":"username","param_value":"gaussdb"}]}'
post "$I" '{"dataIp":"10.0.0.9","id":"4","param":[{"param_name":"sort_col","param_value":"backend_start"},{"param_name":"limit","param_value":"3"}]}'
post "$I" '{"dataIp":"10.0.0.9","id":"5","param":[{"param_name":"threshold_ms","param_value":"0"},{"param_name":"begin_time","param_value":"2020-01-01 00:00:00"},{"param_name":"limit","param_value":"3"}]}'
```

每条期望：

- [ ] 响应键**恰好** `result` / `task_id` / `call_type` / `status` 四个
- [ ] **没有** `code` / `msg`（与接口一结构不同）
- [ ] `status` 为 `"finished"`，`call_type` 为 `"sync"`
- [ ] `task_id` 形如 `grmp-<uuid v4>`，每次调用不同
- [ ] `result.type` 为 `"array"`

### 4.2 全字段字符串化 【实】

```bash
post "$I" '{"dataIp":"10.0.0.9","id":"1"}' | python3 -c "
import sys,json
for row in json.load(sys.stdin)['result']['data']:
    bad = {k:v for k,v in row.items() if not isinstance(v,str)}
    print('非字符串字段:', bad or '无')"
```

期望：`无`。含 oid、int、bool 在内所有列都是字符串。

对照客户 §5.7 样例应看到：`"datdba": "10"`、`"datconnlimit": "-1"`、`"datistemplate": "f"`、`"datacl": ""`。

### 4.3 布尔与 NULL 的渲染 【矛】【推】

```bash
post "$I" '{"dataIp":"10.0.0.9","id":"1"}' | grep -oE '"datistemplate": "[^"]*"|"datacl": "[^"]*"'
```

期望：`"datistemplate": "f"`、`"datacl": ""`。

> ⚠️ **这条通过不代表正确。** 客户文档 §3.1 给的是 `true`/`false`，§3.2 给的是 `t`/`f`，同一中间件同一张表两种渲染。我们默认取 `t/f`，**没有依据**。
> 切换验证：`--bool-style true_false` 重启，应变成 `"true"`。
> NULL 渲染成空串是推断，副作用是 **NULL 与空串不可区分**。

### 4.4 参数结构 【实】

```bash
# 旧形状（接口文档 3.2 的错误示例）
post "$I" '{"dataIp":"10.0.0.9","id":"3","param":[{"param_name":"username","data_type":"String","required":true,"description":"gaussdb"}]}'
# param_value 传数字而不是字符串
post "$I" '{"dataIp":"10.0.0.9","id":"2","param":[{"param_name":"active_only","param_value":true},{"param_name":"limit","param_value":5}]}'
# 重复参数
post "$I" '{"dataIp":"10.0.0.9","id":"3","param":[{"param_name":"username","param_value":"a"},{"param_name":"username","param_value":"b"}]}'
```

期望：三条都 `status:"failed"`，且错误信息指明问题。

### 4.5 缺参数不猜测 【发明】

```bash
post "$I" '{"dataIp":"10.0.0.9","id":"5","param":[{"param_name":"limit","param_value":"3"}]}'
```

期望：`status:"failed"`，点名缺 `begin_time, threshold_ms`。

**为什么不猜**：把未传的条件删掉会静默改变 SQL 语义——「没有慢 SQL」和「没传阈值」变得无法区分。

### 4.6 失败响应的结构 —— 本实现发明 【发明】

```bash
post "$I" '{"dataIp":"10.0.0.9","id":"9999"}'
```

期望：

- [ ] `status` 不是 `"finished"`
- [ ] **没有 `result` 键**
- [ ] 有 `task_id`（失败也是一次任务，日志要能关联）
- [ ] `msg` 里有可读的错误原因

> ⚠️ **客户环境这一分支的真实结构未知**（文档零样例）。我们选择不产出 `result`，
> 是为了让盲目取 `resp["result"]["data"]` 的调用方**当场 KeyError**，
> 而不是安静拿到 `[]`，把「执行失败」读成「当前没有慢 SQL」。

### 4.7 SQL 执行失败 【发明】


期望：`status:"failed"`，`msg` 含 `does not exist`，无 `result` 键。

## 5. 类型校验与注入（重点）

### 5.1 受约束的四种类型能挡住注入 【发明】

```bash
post "$I" '{"dataIp":"10.0.0.9","id":"5","param":[{"param_name":"threshold_ms","param_value":"0 OR 1=1"},{"param_name":"begin_time","param_value":"2020-01-01 00:00:00"},{"param_name":"limit","param_value":"3"}]}'
post "$I" '{"dataIp":"10.0.0.9","id":"2","param":[{"param_name":"active_only","param_value":"True"},{"param_name":"limit","param_value":"5"}]}'
post "$I" '{"dataIp":"10.0.0.9","id":"5","param":[{"param_name":"threshold_ms","param_value":"0"},{"param_name":"begin_time","param_value":"2020/01/01 00:00:00"},{"param_name":"limit","param_value":"3"}]}'
```

期望：三条全部 `failed`。

- INTEGER 只认 `^-?[0-9]+$`
- Boolean 只认小写 `true`/`false`（`True`、`1`、`t` 一律拒绝）
- DateTime 只认 `yyyy-MM-dd HH:mm:ss`

**验证它是在连库前拦住的**：服务端日志里不应出现对应的数据库错误。

### 5.2 ⚠️ String 参数可被注入 —— 这是设计上接受的结果，不是 bug

用一个**不存在的用户名**，对比才干脆（正常应为 0 行）。把下面两行存成
`/tmp/inject.sh` 再执行，避免命令行里多层引号转义出错：

```bash
cat > /tmp/inject.sh <<'SH'
I=http://127.0.0.1:8769/icbc/paas/aiops/grmp/diagnostic/agent/common-operations/invoke
call() { curl -s -X POST -H "auth: $GRMP_AUTH_TOKEN" -H "Content-Type: application/json" \
         -d "$1" "$I" | python3 -c "import sys,json;print('rows =', len(json.load(sys.stdin)['result']['data']))"; }

echo -n "正常   : "
call '{"dataIp":"10.0.0.9","id":"3","param":[{"param_name":"username","param_value":"no_such_user_zz9"}]}'

echo -n "注入   : "
call '{"dataIp":"10.0.0.9","id":"3","param":[{"param_name":"username","param_value":"no_such_user_zz9'"'"' or '"'"'1'"'"'='"'"'1"}]}'
SH
bash /tmp/inject.sh
```

**期望输出**：

```
正常   : rows = 0
注入   : rows = 18        ← 数字随当前会话数变化，要点是「远大于 0」
```

渲染过程：

```
模板   where usename = '{{username}}'
取值   no_such_user_zz9' or '1'='1
渲染   where usename = 'no_such_user_zz9' or '1'='1'      ← 条件恒真，返回全表
```

**为什么不修**：

1. 这是文本替换的固有结果。客户中间件若同样用 `String.replace` 实现（最简的 Java 写法），**客户环境存在同一个洞**。
2. 修了就是本地比客户更安全——本地测不出客户会出的问题，正是我们要避免的。
3. 注册工具已把它标为 `STRING_PARAM` 风险，摆到台面上由人决策。

**这一条应作为发现上报客户**：请其确认 GRMP 对 String 参数是否做转义/绑定。若不做，其现有脚本库里所有带 String 参数的脚本都有同样问题。

### 5.3 标识符位的注入面 【发明】

```bash
post "$I" '{"dataIp":"10.0.0.9","id":"4","param":[{"param_name":"sort_col","param_value":"backend_start"},{"param_name":"limit","param_value":"3"}]}'
post "$I" '{"dataIp":"10.0.0.9","id":"4","param":[{"param_name":"sort_col","param_value":"usename"},{"param_name":"limit","param_value":"3"}]}'
```

期望：两次返回**排序不同**的结果——证明文本替换在标识符位真的生效了。

**对照意义**：若改用绑定变量，两次结果会**完全相同**（按常量排序 = 不排序），且不报错。这正是不用绑定变量的原因。

|---|---|---|---|
| 6.1 | 正确令牌 | `code:"0"` | 【实】 |
| 6.2 | 错误令牌 | **HTTP 200** + `code:"1"` | 【发明】 |
| 6.3 | 不带 `auth` 头 | HTTP 200 + `code:"1"` | 【发明】 |
| 6.4 | 用 `Authorization: Bearer <token>` | `code:"1"`（头名必须是 `auth`，无前缀） | 【实】 |
| 6.5 | 用 `Auth:`（大写 A） | `code:"0"`（HTTP 头名大小写不敏感） | 【规】 |
| 6.6 | GET 请求 | HTTP **405** | 【规】 |
| 6.7 | 未知路由 | HTTP **404** | 【发明】 |
| 6.8 | 路径带 `/dataip/1.2.3.4/`，body 里 dataIp 正确 | 成功，以 body 为准 | 【实】 |
| 6.9 | 非法 JSON 体 | HTTP 200 + `code:"1"` | 【发明】 |

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X POST -H "auth: wrong" -d '{"dataIp":"10.0.0.9"}' "$B"      # 200
curl -s -o /dev/null -w "%{http_code}\n" -X GET  -H "auth: $GRMP_AUTH_TOKEN" "$B"                      # 405
curl -s -o /dev/null -w "%{http_code}\n" -X POST -H "auth: $GRMP_AUTH_TOKEN" http://127.0.0.1:8769/nope # 404
```

**要点**：业务错误一律 HTTP 200，HTTP 状态码只用于传输层问题。只判 `resp.ok` 的客户端会把业务错误当成功。
